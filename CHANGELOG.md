# Changelog

This is the release history that used to live in `manifest.json`'s `description` field.
The manifest now carries a single line, because Chrome documents that field as short text
(the Web Store caps it at 132 characters) and the extension itself is loaded unpacked, so
nobody ever read the history from there anyway.

Every entry below is the original prose, verbatim — only the headings and blank lines are new.

## 0.3.0 – 0.3.5 (initial feature set)

Records gomoku.com move order from the game socket, identifies the RIF opening, runs the Rapfi engine offscreen (multi-threaded or single-threaded fallback, global or stepwise), archives every game and replays it in the built-in viewer.

## 0.3.6

0.3.6 ships in 8 languages (zh-CN / zh-TW / ja / ko / en / ru / fr / de), switchable from a right-click menu on the toolbar icon or the viewer's settings page, and repaints the panel and the viewer the instant the setting changes. Stored identity values (tags, annotation labels, risk levels, opening codes) stay canonical so the learner keeps matching them by literal, and only their display is translated; error text travels from the offscreen engine as codes and is translated by whichever surface shows it. Adds a 📋 copy button to the panel header that puts the whole verdict on the clipboard as one line: model, both players, hand count, opening name and each side's AI rate. It also lets a board snapshot that arrives exactly one move ahead of the socket confirm that stone when its own event lands late, so a hand the server did report no longer counts as having no order.

## 0.3.7

0.3.7 makes game-end detection independent of any single page signal: it snapshots the board when a game ends, when a draw is declared, when the player starts a new game, and when the board is cleared or rebuilt, so a game that stopped mid-way is still archived and is never overwritten by the next one; the settlement wording (rematch / draw) is read as a fallback trigger too. It defaults the thread count to half the available cores (a 32-thread host defaults to 16, up from the old cap of 8), and ranks a four-three kill above a live four when deciding that the game is decided, so a losing side that opens a live four no longer ends the analysis early.

## 0.4.0

0.4.0 checks for its own updates over the network: because the extension is loaded unpacked from GitHub rather than installed from the Chrome Web Store, requestUpdateCheck() can never see a new release, so the latest version is read from a version.json in the repository root, compared segment by segment, re-checked at most every 12 hours on startup and on demand from a button in the settings page, and announced with a flow-layout banner at the top of the panel and under the viewer's navigation bar — a banner that pushes the UI down instead of covering it and can be dismissed for that one version for seven days. It also regroups the settings page into labelled sections on a multi-column auto-fill grid (1 column on a narrow window, 3-4 on a wide one) with the archive and sample statistics as side-by-side cards, and softens the white-side row in the four step tables from #f5f5f5 to #DCDCDC so a long review no longer glares.

## 0.4.1

*(Not migrated from the old description — the entries above are the verbatim manifest history; this one is written for the changelog. The same text is shipped to installed copies through `version.json`'s `releaseNotes`.)*

0.4.1 makes a captured game survive a hostile socket. A repeated coordinate used to cut the record short — the loop `break`ed, so a sixty-move game that replayed one position arrived as twelve moves and looked like an ordinary short game; repeats are now skipped with `continue` and counted in `meta.dropped`. Every timestamp is now an absolute `performance.now()` from the page's own clock (it used to be measured from a per-game origin that meant nothing outside the hook), with a `clockNow` field letting the collector verify the two JavaScript worlds really share a time base instead of assuming it — hands merged in from the board still carry no time at all, because a missing interval is better than an invented one. Archives are labelled with a data-quality verdict (good / partial / suspect) that is displayed and never fed into a score, and the viewer derives it for pre-0.4.1 archives too. Switching language repaints the interface immediately, including the fifteen step columns and the ▾ column menu, which used to stay in whatever language the page had loaded with. The analysis snapshot is taken once at job start so an archived board and its report can no longer disagree. And once the sample library grows 20% past the count the learner was last trained on, both the learning panel and the settings page say so.

## 0.4.2

*(Written for the changelog, like 0.4.1 — the entries above are the verbatim manifest history. The same text is shipped to installed copies through `version.json`'s `releaseNotes`.)*

0.4.2 identifies the opening of a game the detector joined late, and adds a third kind of suspicious hand. Identification used to require three stones in order; it now falls back on position, because black 1 is pinned to tengen by the definition of an opening — so with two stones on the board (black tengen plus one adjacent white) the family is all that can be known and all that is claimed (直止 / 斜止), and with three stones whose order was never captured each stone's role is recovered from where it stands (one black on tengen, one adjacent white, one black inside the central 5×5) and the exact opening is named; an unordered board of four or more still refuses, because a later black stone sits in the same central square and "black 3" stops being identifiable inside the set. `detectOpening` now reports a `stage` of `opening` or `family`, a family capture is shown as 直止（大类，具体开局待定）, and it deliberately writes no opening name into the archive — but the archive does carry a derived opening family, so the 大类 filter still finds such a game instead of filing it under 未识别, which is what the one-shape-one-answer rule at the list card requires.

The new detection technique is the evasion move: one deliberately bad hand — a loss of at least 0.20 win rate, and not the top pick — planted between two good ones (both Top-1, both under 0.05). That hand is then *excluded* from the main statistics, because a deliberate blunder would otherwise dilute the very Top-1 agreement, ACPL and outside-Top5 rate that it is evidence about; the operator would be shown a human-looking ACPL produced by the smoke screen rather than by the play. Two further signals carry the evidence instead, and both are scored: a regular rhythm of evasions (three or more, with the coefficient of variation of the gaps between them — evenly spaced scores high, noisy blunders score zero) and 将胜乱下, a hand that gives up 0.20 of win rate while the side was already winning (best move win rate ≥ 0.85), which is counted whether or not the hand qualifies as an evasion — throwing away a won position is reported on its own. The step table gains a sixteenth column with its own teal badge, the metric summary gains 回避手 N 次（规律性 X）and 将胜乱下 N 次, and the contribution breakdown gains the two new terms. Their weighting is deliberately a surcharge and not a re-split of the same 1.0: the six 0.3.1 terms keep their own sum of 1.00 and the two new ones carry 0.06 and 0.04 on top of it, so a game with no evasion scores bit-identically to 0.4.1 (verified to 1e-12), and the learner normalises the two groups separately so neither can quietly eat the other's budget. All five thresholds are configurable and learnable. Switching language also repaints the archive and sample detail panes now, which are built in JavaScript and used to stay in the load-time language while the column menu beside them switched.

## 0.4.3

*(Written for the changelog, like 0.4.1 and 0.4.2 — the entries above the 0.4.1 heading are the verbatim manifest history. The same text is shipped to installed copies through `version.json`'s `releaseNotes`.)*

0.4.3 fixes a blind spot on the only-move scale and builds two features on top of the fix. The blind spot was that "playing like the engine" was measured exclusively as Top-1 agreement: a hand ramped from 0 below 72% Top-1, and the only-move term counted a sharp hand only when the played move *was* the single best one. But an opponent who consistently lands on the second through fifth best move is not playing like a human either — a strong engine still finds most of those hands within its top five — and a game of such hands scored in the fifties where it should have scored in the eighties. A near-miss is now graded rather than ignored: a new proximity step gives the Top-1 pick 1.0, the Top-2/3 picks 0.75 and the Top-4/5 picks 0.55 (anything worse, 0), the Top-1 ramp reads the average of that step across the side's hands instead of the Top-1 hit rate itself, and the only-move term averages the same step across the sharp hands instead of counting hits — so a sharp hand that takes the second-best move now counts, at 0.75. The two old Top-1 cut lines stay in storage and in the learner, but the detector only reads them when the caller explicitly asks for the legacy behaviour, which is what makes the before/after comparison testable; the new cuts ship at 0.50/0.90 and are themselves configurable and learnable, re-anchored on the quantity the ramp actually reads rather than on the hit rate it no longer uses. Nothing about the weight structure changed: this is a new set of thresholds, not a re-split, so the six terms still sum to 1.00 with the two 0.4.2 surcharges on top and a game with no evasion is untouched.

The first feature is segmentation. Every one of a side's own hands is classed as inside or outside the top five, that binary sequence is run-length encoded over the side's own move order (the opponent's hands are not part of the run — 段 counts *my* hands), runs shorter than three hands are merged into the neighbouring run so a single lucky excursion does not carve the game into noise, and the result is mapped back onto global move numbers and stored as `report.segments`. All four step tables draw it as a 4px left rail on the row's own move number — green for a run that stayed inside the top five, orange for one that left it — a heavier rule at each boundary, and a one-line legend under the header. The segments are editable: an operator can drag either edge of a run with a live preview (each side keeps at least one hand, so a drag clamps rather than empties a segment), or right-click a hand to create a segment of one move, to the end of the current run, or over a hand-picked range, and right-click inside a manual segment to discard the overrides and go back to the automatic rail. A hand-picked range is re-coloured from the hands it actually contains rather than inheriting both ends, so a range spanning both classes splits into two correctly coloured pieces. The manual list is per side and per game, persisted through the same serial write chain as everything else, and additive: a pre-0.4.3 archive simply has no manual list and renders the automatic rail.

The second feature is a classification on top of the score. The five bands of the risk number now have names, and inside the AI band the class depends on segmentation: a side whose hands stayed in the top five throughout is a low-level AI, one with a few hands outside is an evasive AI, and one with four or more is a strongly evasive AI — while the four bands below are 疑似AI, 职业选手, 高手玩家 and 普通玩家. The class is shown as a badge on the archive and sample list cards and in both detail panes, and can be overridden by hand from a dropdown, which marks the badge and updates the list; the override is stored beside the automatic answer rather than replacing it, so clearing it restores the automatic one. As with the risk levels, the class is persisted as a stable code (it is computed in the offscreen document, where no UI dictionary exists) and only its display is translated — the seven codes were added to the semantic core and to the runtime-key map so all eight tables carry them.

Finally, the sample editor showed per-step verdicts after an analysis but never the number they add up to. It now carries an 评估结果 panel with the same two risk cards and the same metric table as the detect pane and the replay detail — one renderer, so the three panes cannot print different readings of the same game — filled immediately when an already-analysed sample is opened, refreshed when a run finishes, and cleared back to 分析后显示 the moment an edit invalidates the board it described.

## 0.4.4

*(Written for the changelog. The same text is shipped to installed copies through `version.json`'s `releaseNotes`.)*

0.4.4 gives the detector a voice, and makes it ask. When a game starts it sends one fixed anti-cheat statement into the game chat — English, once per game, within the first thirty seconds, and only after the operator has confirmed it the first time, because talking to a stranger on someone's behalf is not something an extension should start doing on its own. From then on it answers in the language the opponent actually wrote in: the reply language is chosen from the message itself (CJK ratio, kana, hangul, Cyrillic, Latin stopwords, with full-width ？ and half-width ? told apart) and is deliberately independent of the interface language, so a Chinese UI can still answer a Russian opponent in Russian; eight languages of greeting/thanks/where-from templates rotate at random with a ten-second floor and no immediate repeat, and a message that carries no recognisable language at all gets one line — "where are you from?". Whoever sent a message is identified in three falling-back levels — the socket's own player list, then the page's DOM, then the announcement anchor — and the answer is allowed to be *unknown*: when the sender cannot be placed, nobody's risk number is touched. The one automatic exception is the opening question, which is only asked of a side already above 65%.

The second half is the F&Q: a bank of questions, transcribed from the operator's own file as a dialogue tree rather than a flat list, asked by hand from a button in the panel or automatically past the 65% line, with a sixty-second window for the answer. The first question asks whether the opponent has studied gomoku — a plain yes lowers the AI rate, a no raises it — and the second only exists once the rate is past 55%: it asks whether the opponent can name this game's opening, and if they say they are a beginner it follows up by asking them to name it for you, grading the answer against all 278 opening names across the eight languages (not just the current one) and closing with a thank-you. Grading maps to a verdict — correct, wrong, an explicit refusal, an off-topic answer, or no answer at all — and only the last two are free: correct costs −10, wrong adds +8, and the whole channel is capped at three adjustments per game and a cumulative swing of ±20, always applied to the opponent and never to the player. The adjustment is stored beside the measured score rather than inside it, so the engine's reading of the board is still there to compare against. Finally, an optional LLM endpoint (default off, key stored locally and nowhere else, request routed through the service worker so the page's origin cannot bind it) can be used for the questions the bank cannot cover; it falls back to keyword matching on failure, and disables itself for a day after three failures in a row.

*(Written for the changelog, like 0.4.1–0.4.3.)* The chat shipped above did not work, and the operator said so in six words: 「信息未能正常发送，问题没有发送途径」 — nothing went out, and the 提问 button had no way to send anything. Three separate faults were behind it, none of which the test suite could see because no suite ever drove a browser against a controlled input.

The first is that §7.3's own snippet — `input.value = text`, then dispatch, then `return true` — is wrong twice over. A framework's controlled input wraps the element's `value` property so that a write updates both the DOM *and* the framework's own value tracker; the framework then fires its change event only when the DOM differs from that tracker, so assigning through the wrapper leaves the DOM correct, the tracker in agreement, and the app's send handler running with an empty string. The text is visible in the box and nothing is sent — which is exactly the reported symptom, and it defeats any check that only asks "is the text there?". The write now goes through the prototype's own setter, which the wrapper does not intercept, so the tracker stays stale and the change event fires. The second half of the same line, `return true`, reports success for having dispatched events, so every failure looked like a success and the retry loop never ran. A send is now *verified*: the app clears the box when it accepts a message, so text still sitting there a beat later counts as a failure, and the code then tries a nearby send button before giving up. The third fault is that the sender's colour was only worked out inside the incoming-message handler — but the 提问 button is gated on that colour, so it could not send the first message, and only the opponent speaking unprompted could break the deadlock. The colour is now resolved proactively from every socket frame, from the tick, and before the gate is consulted; the socket's seat list carries the player ids it always had and hook.js was throwing away, because `selfId` is an id and an id cannot be matched against a name. An unknown colour no longer blocks the explicit 提问 button either — §9 already guarantees that nothing is adjusted in that state, and blocking on it made the button permanently dead whenever the seats could not be read; the automatic prompt keeps the strict gate, since it has to name the side whose rate crossed the line. A failed send now says which of the three things went wrong instead of one sentence for all of them, and the reason stays on screen in the question panel after the footer's five seconds are up. A statement that fails to send is also no longer recorded as delivered, and no longer retried on every tick for the rest of the thirty-second window.

*(Written for the changelog, like 0.4.1–0.4.3.)* The panel's two verdict cards printed the engine's risk score at full precision — 17.3215408586938 and 64.37268497974357 — because the display-time chat adjustment handed the untouched float straight back whenever it had no adjustment to apply. The number is now formatted in one place and to one decimal, which is enough to see the chat adjustment move it and not enough to imply the engine resolves hundredths; the compact panel and the job queue's black/white pair go through the same formatter, so they can no longer disagree. The same function also answered a second question by accident: whether to print 「交流 N」 was decided by comparing the displayed number against a rounded copy of itself, which is unequal for every float — so a game with no chat exchange at all still advertised 「交流 0」 on both cards. That is now a fact about the adjustment, not about the string. Making it a fact about the adjustment turned out not to be enough: the first fix asked only whether an adjustment existed, which put the annotation on *both* cards whenever one did, so the card whose number had not moved carried a note claiming it had — contradicting §13.3's 「只影响对手」. The line now names the same side the adjustment landed on. The mapping that decides which side that is had been copy-pasted into three places — the archive record, the automatic prompt's risk lookup and the display — and is now one function, so a single character can no longer invert the adjustment at two of them with nothing to notice. Both faults were found by rendering the real cards with the real stylesheet and reading the text the operator reads; the suite had asserted the formatter's source shape throughout and stayed green.

Collapsing those three copies into one function then exposed a third fault, and a worse one: the mapping was inverted. `chat.senderIsBlack` holds the SENDER's colour — the seat lookup matches on our own `selfId`/`selfName` and returns *our* colour, and `resolveSenderColour` negates it — so `true` means the opponent is black and the side that must move is black. The code returned `'W'`, which sent every adjustment to the player who had never answered a question, and sent the automatic prompt's risk lookup to the same wrong side, directly against §13.3's 「只影响对手」. It had no test at all, and could not have had one while the expression existed in three copies: a suite that only asked "did exactly one side move?" passes on an inverted mapping. The mapping is now asserted outright, on the side that §13.3 names, and the chain that makes it correct — the seat match returning our colour, the negation producing the opponent's — is pinned alongside it.

## 0.4.5

*(Written for the changelog, like 0.4.1–0.4.4. The same text is shipped to installed copies through `version.json`'s `releaseNotes`.)*

0.4.5 adds a second site. Every site-specific decision — the URL match, the board container, the per-cell grammar, the stone encoding, the chat field, the end-of-game hints, and whether the socket is worth polling — now lives in one `sites.js` table, and `content.js` and `hook.js` only ask it what the board looks like on this host. gomoku.com's five cell selectors and six chat-input selectors are carried over byte for byte, so the adapter changes nothing there; the file is listed in both worlds (before `hook.js` in the page's MAIN world, before `content.js` in the isolated one) because a second copy of a config is the thing that drifts.

papergames.io is an Angular + Angular Material client whose board is a real `<table class="table-board">` of 225 `td.cell-<row>-<col>`, with a played cell holding one `<svg class="symbol">` around one `<circle>`. It exposes no `window.socket` or `window.io`, so `hook.js` skips its socket poll entirely and DOM collection carries the site on its own; the board being torn down when a game ends (verified: 225 cells to 0) is used as the end signal instead, behind a move floor and a grace period so a re-render cannot end a game that never started.

The spec's papergames selectors were a 探测性回退 list and three of the four facts it asked to be confirmed by F12 turned out to be wrong in ways that fail silently, so they were settled by driving the live site instead. Its rows are numbered from the TOP while gomoku.com numbers from the BOTTOM and everything downstream is written against gomoku's convention, so the row has to be flipped once — a missed flip mirrors the board, which analyses perfectly well and means nothing. A cell the mouse hovers is given a preview stone with the same markup as a real one and only `.clickable` distinguishes it, so the first version of the board reader invented a stone wherever the cursor rested. And the circle class is the PLAYER's colour, not a gomoku colour: the badge assignment is stable (the human is `circle-light`, the robot `circle-dark`) but the site hands the opening move to either colour — sampling both clocks every second caught the robot opening with its own clock running, and other sessions with an empty board and ours — so black is now derived from play order, using gomoku's own invariant that black moves first and therefore has at least as many stones as white.

The panel's header gains a 🌐 language menu and a ⚙ rule menu. The language list is the same `GMI18n.LOCALES` + 「跟随浏览器」 the viewer's settings page uses, and the rule list is 自由 / 标准 / 连珠 plus 自动, stored in a new `settings.rule` where `null` means "infer from the site" — which is what makes 连珠 analysable on a site with no renju path at all. Both write through the existing setting path, so the panel, the viewer and the copied output repaint from the one `chrome.storage.onChanged` broadcast. A single `ruleCode()` now owns "which rule is in force" and every label is derived from it, because the same decision was about to be written in three places and this project has twice shipped a silently wrong answer that existed in three copies.

Finally, 开局排除 did nothing on the engine path. `analyzeGame`'s `needEngine`, `analyzeStepwise`'s `need`, `analyzeStep` and the progress denominator all skipped the `isOpening` check, so the first N hands per side were analysed by the engine and then discarded by `sideAggregate`'s filter — the operator paid for engine calls whose results could never be used. They are now skipped before the engine is touched, while the shape test still runs on them, because a live four formed inside the opening is rare but real and dropping the test there would let detection run straight past it. The spec's §3.2 rationale and its fourth fix were both adjusted: `playerIdxByMove` is the global move ordinal (`analyzeStep` derives its parity fallback from it), so `openingCutoff = 8` excludes the first eight MOVES, not eight per side — the saving is 8 engine calls, not 16; and `liveStepFor` deliberately keeps its round trip, because offscreen's live session IS the archived report and returning early there would delete the opening rows from the table and shrink `totalMoves`.

The manifest's one-line `description` is reworded to fit inside Chrome's 132-character cap again. Naming the second site pushed it to 144, which the full regression caught in five suites at once — the field has been capped since 0.4.1, when the release history moved out of it and into this file.

## 0.4.6

0.4.6 fixes the names a papergames.io archive carries, and takes the UI from 8 languages to 13.

Archives from papergames.io had `players` filled with nulls, and their title read "Unnamed game" in English (「未命名对局」 in Chinese) — a 42-move game with a risk score of 85 looked like a broken record. Two causes, and the second is the one that was visible: `content.js`'s `playerNames()` only knew gomoku.com's selectors, and `viewer.js`'s `displayName()` jumped straight from "no names" to 「未命名对局」 without ever saying what it did know. The title now degrades in three levels — a colour-mapped pair, then self/opponent, then 「黑方 VS 白方」 — so an unreadable name and an unnamed game stop looking alike. `defaultArchiveName()` gained the missing branch for a half-known colour pair, which used to drop the one name a record actually had.

The spec's plan for reading the names was to treat the first of the two side-by-side players as self, and the live site says that is wrong exactly where it matters. `app-room-players` renders two `col-6` slots that are always `[circle-light, circle-dark]`, but which of the two is the local player moves: three robot games put us in slot #0, and a game against a human put us in slot #1 with the opponent in #0. A swapped "A VS B" reads perfectly well, so the error would have been silent and permanent. Nothing near a name carries a colour either, so the two names are recorded as self/opponent — a claim the reading supports — and never as black/white, which it does not.

Orientation therefore needs an independent statement of our own nickname, and the only one on the page is the sidebar account menu. Its structure is a trap: `app-user-menu`, `span.user-profile` and `div.name-credit` all read `"detectorprobe 2000"` — the nickname AND the credit balance — so an equality test against a player name can never succeed. Only the nickname's own `div` holds the bare name, and that is what `sites.js` selects. A pair that could not be oriented is recorded as `dom-pair-order` rather than `dom-pair`, because "I read two names" and "I know which one is you" are different claims and the viewer's 玩家名来源 row now says which one it has.

There is also a timing problem the spec did not mention: papergames.io tears the room down when a game ends, which is how the ending is detected at all, and the record is built after that. Reading names only at finalize time would therefore find the player row already gone. The panel tick now remembers the last complete read, and the record falls back to it — but only on a site whose board disappears at game end, so everywhere else the live DOM stays the single source of truth.

The UI now ships in Vietnamese, Spanish, Malay, Arabic and Mongolian alongside the original eight, as thirteen tables of 911 keys each, verified key-for-key. Arabic is the one with real work in it: the shell mirrors through CSS logical properties (`margin-inline-start`, `border-inline-start`, `text-align:start`), which viewer.html now uses exclusively — all 18 of its physical properties were converted. The board is deliberately NOT mirrored: a gomoku coordinate is the same intersection whatever language the operator reads, and mirroring the canvas would move every move in the replay by one reflection. Digits stay Western (`0123456789`), because the same numbers are printed for coordinates, move counts and risk scores and the app parses what it prints.

One trap is worth recording because it would have looked like the RTL work simply did not apply: the panel's `:host{all:initial}` resets `direction` to `ltr`, and the `dir` attribute is only a presentational hint (specificity 0), so the author declaration wins and the attribute is ignored. The panel therefore re-asserts its direction from the attribute itself, with `:host([dir="rtl"])`. Setting `dir` on gomoku.com's own document was never an option either — that would mirror the host page's board and chat around us.

The language pickers (panel menu, viewer settings, and the toolbar's context submenu) now label each entry through `GMI18n.langLabel()`, rendering 「English（英语）」 — the language's own name plus what the current language calls it. The endonym comes from the locale tables, not from `Intl.DisplayNames`, which answers 「中文（中国）」 for zh-CN and lower-cases 「русский」 and 「монгол」; Intl supplies only the local half, and the whole thing falls back to the bare endonym when it is unavailable.

## 0.4.7

0.4.7 adds a detection signal, tightens an existing one, and gives the UI a theme.

The new signal is a run of fours. A single four is ordinary gomoku — you play a four, the opponent must answer it, the game moves on. What is not ordinary is a side that keeps making fours that have no point: they force a reply, gain nothing, and are made again. `markFourRuns()` walks each side's own sequence, groups consecutive fours into runs of two or more, and labels each run by the win rate the side had BEFORE the run started — copied onto every step as `prevBestWR`, because the rate at the moment of the four is the rate after it already worked. A run that started from a winning position (≥ 0.90) is a VCF and is not scored at all: that is a winning line being executed, not a symptom. A run that started from a lost position (≤ 0.10) is 无用冲四 and is the one that scores. Everything between is reported as 防御性冲四 and contributes nothing, because "the opponent was threatening and this was the only reply" is a legitimate reason to make a four and the run is the defence, not the offence.

The surcharge `aUselessFour` joins `evasion` and `winBlunder` OUTSIDE the six base weights, which still sum to 1.00 — the same arrangement 0.4.2 established, and for the same reason: the six terms describe how the moves look, and these three describe a pattern across moves. Weight is 0.05 (the spec named it twice at that value; the sentence comparing it to 将败冲四 would have put it at 0.08, and for a brand-new signal the lower number is the safer one to be wrong at).

Top2-5 proximity is raised again: 1.0 / 0.80 / 0.50 for Top1 / Top5 / Top8, and the `topProxLo` ramp now starts at 0.45 instead of 0.50. The three tiers replace the old two, so a Top3 hand no longer scores identically to a Top1 one — 0.4.3 §1.1 had already made this point and this is the next step along it.

阶段性臭棋 is now a property of the SEGMENTATION, not of the classifier. The merge pass that used to fold a short `low` run into its neighbours now skips `low` runs entirely, so a burst of bad hands inside an otherwise strong game survives as a run instead of being smoothed away — and that run is exactly what the classifier reads. Classification counts them: no low runs is 低级AI, one run of two or fewer hands is 规避型AI, and two or more runs OR any single run of three or more hands is 强规避AI. The "or" matters: one long collapse and two short ones are different stories but the same verdict, and a classifier keyed on the count alone would call the second one a weaker player than the first.

The engine is asked for Top8 instead of Top5 when the recorded thinking time exceeds 6 seconds. A hand that took that long is a hand the player was computing on, and the extra candidates are the evidence of what they were choosing between. It is per-step, not per-game, and the column is now 「候选（前5/8）」 so the header does not claim a width the data may not have. The step-table legend repeats the rule inline («TOP8 扩展（思考 > 6s）»), because a reader who does not know about the 6-second cut reads four empty candidate cells as "the engine found nothing there" rather than "this run did not ask".

All three four-run classes are reported, in two places. The 指标汇总 table gains a 冲四序列 total plus one row per class, and the detail pane's fact list carries the same three numbers on one line — VCF and 防御性 are shown even though only 无用 moves a score, because a column of zeros under two labels is the clearest possible statement that those two are not being punished. The 贡献分解 panel used to print its components as their raw identifiers, so the new term read `uselessFour 2.5`; it now resolves them through the same `learn.weight.<key>` runtime key the learner's own weight table uses, which is also what keeps the panel and that table from ever wording one component two different ways.

Two panel fixes. The compact (缩略) face was sticking at 99%: its finished-check ran AFTER the running-check, so a job whose progress had reached 99 while still marked 分析中 kept drawing the progress bar even after it finished — and the one number that would have ended the loop was the one the check never reached. `liveFinish()` now sets the progress to 100 unconditionally, and a failing job is floored at 99 rather than left at whatever it had reached. Both are the same bug from opposite ends: a progress that never arrives at its terminal value.

And the theme. `settings.theme` is `dark` / `light` / `auto`, defaulting to `auto`, with `auto` resolved by a CSS `prefers-color-scheme` media query rather than in JavaScript. That is deliberate: the attribute is the only thing JS writes, so there is no flash of the wrong palette on load and no listener to keep correct — an OS theme flip repaints because the stylesheet says so. The panel gets it on the Shadow Host (`data-theme`), the viewer on `<html>`; both are the root of their own document, which is why they are not the same line of code. In the light palette the step tables' black and white rows swap their wash values (`#1a1a1a` / `#e8e8e8`), because a `#DCDCDC` row on a white panel is nearly invisible and a `#111` row would be the only dark object on the page.

Transparency mode is a window-level effect only, and the settings page says so. A `chrome-extension://` window is composited by the browser with no per-window alpha, so "transparent" means transparent against the browser's backdrop and cannot show the desktop — promising otherwise would have been the kind of claim that reads fine in a changelog and is obviously false the moment it is used. Within that, the two alphas are deliberately separate: the background surfaces fall from 1.00 to 0.00 with the slider, and the functional widgets stop at 0.80. A window whose buttons are as invisible as its background is not a feature, and the floor is what keeps the close button on screen at level 0.
