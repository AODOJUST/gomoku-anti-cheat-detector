# Changelog

This is the release history that used to live in `manifest.json`'s `description` field.
The manifest now carries a single line, because Chrome documents that field as short text
(the Web Store caps it at 132 characters) and the extension itself is loaded unpacked, so
nobody ever read the history from there anyway.

Every entry below is the original prose, verbatim — only the headings and blank lines are new.

## 1.0.5

**1.0.5 fixes three things a user found by pressing a button, and each was two halves of one feature that had never been read together.**

**1. 分享到聊天室 never once succeeded.** `cmShareGo` sends `chat.send('', { attachment })` — §1.1.2's attachment is a message with no text of its own — while `chat-send` refused *any* blank `content` with `BAD_REQUEST`, which the panel renders as 「发送失败（请求无效，请重试）」. The picker draws no other route into the room, so 发送回放/样本 to the room was dead from 1.0.2 through 1.0.4. Fixed **server-side**: an empty content is now an error only when there is no attachment, and the attachment message is stored with a blank text (the room draws the card from `attachment.kind`, and `cmMsgHtml` already skips the bubble). Because the fix is in the Function, an already-installed 1.0.3/1.0.4 client starts working without being reloaded. The length and censor gates still run on whatever text a share does carry.

**2. 激活界面 vanished at a stray click.** `openModal` bound a backdrop click to `closeModal()` and the global Escape handler closed the top layer too. 激活 asks for five fields and then waits on an email that may take a minute; one accidental click discarded all of it and left no sentence behind. `openModal` now takes `pinned`: a pinned layer does not bind the backdrop, and Escape asks the same `data-pinned` attribute first — two accidental paths, one predicate. Both the 激活码 dialog and the 注册 dialog it opens are pinned, so the only exits are the two controls that say what they do (「关闭」 and 「暂不」). Pinning is **not** the default, and `closeAllModals()` deliberately ignores the attribute so a successful registration can still close itself.

**3. 头像 could never be uploaded — and said the wrong thing when it failed.** Two independent faults. (a) §3.6 names a Storage bucket `avatars` and **nothing ever created it**: `profile-update` has uploaded to `avatars/{user_id}.jpg` since 1.0.1, so every 更换 ended in `Bucket not found` → `INTERNAL` → 「服务端暂时出错，请稍后重试」. No suite could see it: the client half, the server half and even that error branch were all correct, and the missing piece was state, not code. `016_avatars_bucket.sql` creates it (public, 2 MB, jpg/png/webp — the same values as the function's own constants), and `verify-067` pins the function's bucket name against the migration's so the two cannot drift again. (b) `validateAvatar` returned the activation code's `BAD_FORMAT`, so choosing a GIF for an avatar answered 「激活码格式形如 BS-XXXX-XXXX-XXXX-XXXX」; `TOO_LARGE` had no branch at all and fell through to 「未知错误（TOO_LARGE）」. The avatar path now has its own two codes, and the row states the accepted formats and limit up front instead of waiting until a file is refused. Also: the file input is cleared after a pick, so the same file can be chosen twice.

**The same version also carries the second 定稿 (账号与设置 / 管理员系统 / 主页更新) and the RLS and 权限 audit's thirteen findings. The version number is unchanged — the operator's ruling was that the rebuilt archive replaces the one with the same name.**

**§一 切换账号 — and it is not 退出登录.** 退出登录 clears the live session; 切换账号 keeps the credentials of the accounts already signed in on this device and goes straight to another one, **no password**. At most five are kept (the oldest is evicted), re-signing-in to the same account updates the row in place, and ⚠ the ceiling is enforced **in the storage layer** on both the read and the write, so a hand-edited sixth row never reaches the UI either. ⚠ The JWT is sealed with **AES-256-GCM** before it is written (`crypto.js`, new): the key is the **32-character string itself, not 32 random bytes** — §1.1.4's sketch hands `encode(deviceKey)` straight to AES, and GCM accepts only 16/24/32 bytes, so the literal reading would throw `DataError: AES key data must be 128, 192 or 256 bits` on every seal and unseal. The IV is 12 bytes, fresh per call, and travels beside the ciphertext. ⚠ This project has **no refresh token** (1.0.0 signs its own 30-day JWT), so §1.1.3's 「refresh the target's token」 is done by `auth-renew` and the row stores `expiresAt` instead of a `refreshToken` nothing could ever fill; an expired copy, a seal that will not open, and a server 401/403 all become the same answer — the password dialog, with that account's e-mail already in it. The settings page gains a **vertical quick nav**: the rows are not written by hand, they are read off each panel's own `<h2>` (a hand-written list is a second copy of the panel names), a press scrolls to that panel, and `IntersectionObserver` highlights whichever panel is in the **reading band** — ⚠ that is the visible panel, not necessarily the one just pressed. On a build with no activation it lists only the four panels that carry no `data-gate`, which is the gate and the nav agreeing without being told to.

**§二 管理员系统.** The nav entry that had read 「—」 since 1.0.0 is now named 管理员. A **super admin** joins the role set (`users.role`: `user` / `admin` / `super_admin`, closed by a CHECK): the only role that can appoint and dismiss an ordinary administrator (`admin-set-role`, the project's single `requireSuperAdmin`), it cannot dismiss another super admin, and it cannot demote itself — ⚠ all three are decided **server-side**; the client only hides and shows UI, and a local refusal would be a second implementation of a server judgement. ⚠ §2.2.5 「不显示任何标识」: an ordinary administrator's screen does not contain the word 超级 anywhere, and a super admin's page differs by exactly one panel and one nav row — the two share one route and one `renderAdmin`. The 管理员 console gets the **same** vertical nav as the settings page (one function, two ids — not a copy), the user list folds row by row with 展开全部 / 折叠全部, and an expanded row carries 注册时间 / 最后登录 / 状态 / IP 国籍 / 简介. ⚠ The 定稿 sketch also draws 「样本库：42 个 / 回放：128 局」 on that row and they are deliberately absent: `admin-list-users` does not return them and PostgREST cannot `GROUP BY`, so one row's convenience would cost fifty extra queries; both numbers live one panel down, where the operator has already picked a person.

**§三 主页更新.** The 主页 is reshaped into the four blocks the reference profile draws — header (avatar / username / @username / country / bio), 游戏统计 (样本库 / 回放存档 / 检测对局 / 好友), 徽章, and 成就（即将推出）with the 定稿's four names. ⚠ 「主页的样本库数目与实际不符」 is fixed at its root: the old page drew the cloud's `count(*)`, 云同步 is **off by default**, and a sample captured on this device was therefore invisible to the server. The count is now the size of the **UNION** — cloud count **plus** the local rows the cloud does not know — computed by diffing local ids against the cloud's (PostgREST cannot subtract sets, and `count()` would only restate the cloud's own answer); the delta is drawn as a 「+N」 beside the number. ⚠ The 定稿's `syncedToCloud` flag was **not** adopted: `sync.js` has decided 「上云了吗」 by comparing `updated_at` since 1.0.3, and a stored flag would be the third answer to one question — stale the moment another device edits the row. 徽章 are drawn for real from this release (the `badges` table has existed since 001), with the 定稿's five known types and an honest fallback that shows an unknown `badge_type`'s raw name rather than dropping it. The page stays **read-only**: the count of pressable elements on it is 0, asserted by `behave-062`.

**⚠⚠ The RLS / 权限 audit — all thirteen.** **P0-1** 「the migrations' RLS rests on discipline」: `verify-067 §8` mechanises it for **every migration 001–020** (twenty tables) — each `create table` must enable RLS in the same file, nothing may disable it, every writable policy must name `auth.uid()` for itself, and no writable policy may rest on `is_admin()` alone. ⚠ 「a policy exists」 ≠ 「a policy is in force」, which no static check can settle, so the checklist also carries a manual regression: an anonymous `PATCH /rest/v1/global_settings` must return an empty array. **P0-2 / P0-3** 隐藏国籍 and 隐藏最后活跃 hid the flag and left `country_code` readable: `018_user_directory` adds a view with column-level revoke and `are_friends()`, so both are now promises about the **data layer** (a direct PostgREST read gets blanks), and the view's restated row predicate must match `users_select_public` word for word. **P1-1** the `*.supabase.co` host match was too wide → narrowed. **P1-2** a page script could forge `__gm_event` in the MAIN world → `gm-nonce.js` mints a 256-bit key in the **isolated** world and parks it in the DOM, `hook.js` signs every frame with it, and `content.js` accepts nothing without a valid MAC (a real frame passes; unsigned and wrongly-signed ones are dropped as separate reasons). **P1-3** the LLM key and JWT were described as 「plaintext」 → PRIVACY §10/§11 now describe the **data layer**, plus the one honest exception: Realtime presence is **one channel shared by the whole product**, so any signed-in account can see who is online and 隐身 does not remove you from the member list — what it cannot give away is a historical timestamp. **P1-4** `settingsPatch`'s column grant → §8 pins 011's `grant update (…)` to `hide_country` / `manual_status` and 002's to `username` / `bio` / `avatar_url`, and pins `settingsPatch`'s field whitelist so the whole object can never be forwarded. **P1-5** the e-mail code could be guessed without limit → `019` adds an `attempts` column, `bump_email_code_attempt` increments it atomically, and `claimEmailCode` is the single funnel; the ceiling is 5 and the new `TOO_MANY_ATTEMPTS` code is deliberately **not** `RATE_LIMITED` (that is the *sending* cooldown; this is *verification*). ⚠ A burned code is not marked `used` — doing so would make the next verdict fall back to 「验证码错误」. **P2-1** 黑名单 took part in cloud sync by default → it no longer does (`behave-062`'s expected values moved with it: an intentional fix, not a regression). **P2-2** the account-deletion job had no closure → `020` separates 「which code was used」 from 「has it been used up」 (a new `redeemed` column) and turns three RESTRICT foreign keys onto `users` into `on delete set null`; ⚠ otherwise every account that ever redeemed a code carried a RESTRICT reference to itself and the purge would fail with `23503` forever — looking exactly like a month in which nobody deleted their account. `friend-share-purge §4` now really deletes the GoTrue identity, the Storage avatar bytes and the `users` row (plain SQL can do neither of the first two: leaving the identity behind would make that e-mail permanently unregistrable). `verify-067 §10.2` asserts, with an effective-`ON DELETE` algorithm, that none of the **24 foreign keys onto `users`** omits it — ⚠ one new RESTRICT key means deletion can never succeed, silently. **P2-3** the global presence channel → documented as above. **P3-1** the anon key in the realtime URL → the `Sec-WebSocket-Protocol` form was measured and is refused by the server in the handshake, so the query form is the only usable one and the anon key was never a secret; the finding is answered as a **decision with evidence** rather than 「won't fix」. **P3-2** `admin-list-users` returned too much → it now projects. **P3-3** `sessionArea()` fell back to `local` → it no longer persists. **P3-4** `wireCode()` ignored `data.code` → it reads the native code. And **§9** gives each of the **36 Edge Functions** exactly one gate (27 gated + 8 open entrances + 1 cron), asserting that no function is simultaneously callable by anyone and holding the service role.

**Patch (version number unchanged) — the sidebar quick nav could not be seen over a 自定义背景.** The rail shipped with **no fill of its own**: twelve lines of `--mut` text laid directly on the page background. That reads fine over the plain `--bg` and disappears the moment a background picture is set — `html.has-bg` makes `body` transparent and puts the photograph behind everything, so the labels became grey type on bright foliage (「几乎看不见」, and the report was right; the panels were never affected because they have always carried `--panel`). The rail is a **surface** now: fill, edge and radius the same as `.panel`, and — the half that matters — the same entry in the 元素透明度 block at the end of the stylesheet, so it goes to glass **with** the panels instead of staying the one opaque block in a see-through page. ⚠ Two more things ride along, and both are the same defect wearing different clothes. (a) The labels **wrap** now: `sectionNav()` reads each row off its own panel's `<h2>`, and 「检测设置（与页面浮层共享同一份存储）」 needs ~240px against a 200px rail, so `white-space:nowrap` was cutting it off mid-character — and `overflow-y:auto` alone computes `overflow-x` to `auto`, so one long label was enough to put a scrollbar inside the nav. (b) The <900px branch's opaque `background:var(--bg)` is **deleted**, not kept: the block's `background-color` wins against it (equal specificity, later in the file), so it could never take effect — and a rule that cannot take effect is worse than no rule, because the next reader trusts it. The strip is opaque at the default setting for the same reason the panels are. `behave-067-fixes` **B10** measures all of it in a browser: with `has-bg` really on, the rail's computed fill is no longer `rgba(0,0,0,0)`; at 元素透明度 35% the rail and the panel resolve to the **same** fill; below 900px the strip is `row`, squared off, and fully opaque. Only `viewer.html`'s stylesheet changed — no new strings, no new setting, and the detection path is untouched.

**Upgrading.** Migrations run to `020` (twenty tables) and all **36 functions are redeployed as a batch** — ⚠ deploying only the new ones is wrong: `_shared/` is bundled into every function's artifact, so touching it once means redeploying all of them, or an old bundle keeps a `_shared` that does not recognise the new tables and codes and the feature fails silently. The order is fixed: `db push` first, functions second. `PURGE_SECRET` is required and fails closed (the `baishen-purge` cron is what actually deletes deleted accounts). Two of the fixes are server-side (`chat-send`, `profile-update`), so an installed client recovers that half without being reloaded — but the 定稿 half lives in the extension pages (new files `crypto.js`, `gm-nonce.js`, `admin-set-role`), so 1.0.5 still has to be reloaded at `edge://extensions`.

## 1.0.4

**1.0.4 closes four surfaces that LOOKED finished.** Each of them failed the same way — something existed in the source and nothing delivered it — and each failure was invisible from inside the product.

**§P0 The operations panel.** `admin.js` has carried `revokeCodes` / `grantBadge` / `reissueJwt` / `handleReport` / `replyFeedback` / `publishNews` / `setGlobalMute` since 1.0.0–1.0.3 with **no caller in the extension**: the console could only be used from Supabase Studio. The admin view now draws five panels and wires every control in one place — 举报处理 (status filter plus 警告 / 禁言 24 小时 / 禁言 7 天 / 封禁 / 不处理 with a resolution note), 反馈回复 (through `admin-reply-feedback`, reporting 已发送 / 未发送 honestly), 发布公告 (category / language / pin), 聊天室开关 (two booleans over `global_settings`, painted from the RESPONSE and never from the checkbox), 撤销激活码 (by list or 「all unused」), 用户详情 (activation, mute, last seen, registration, country, report history) and 重新签发会话 (the token is DISPLAYED, never installed). ⚠ The panel is built by `renderAdmin()` and wired by `wireAdmin()`, and `behave-066` presses all eight controls — 1.0.0's `buildCloudPanel` is the reason 「the id is in the markup」 is not treated as evidence.

**⚠⚠ Realtime actually arrives (§P1).** `supabase_realtime` was a publication with **zero members**. The client has hand-written the Phoenix protocol since 1.0.2 and declared `postgres_changes` subscriptions in every `phx_join`, and no table was ever published — so 「实时」 was the 6-second poller wearing the word, and `RT.status` reported `'live'` because the join is answered `ok` either way. `013_realtime.sql` publishes seven tables: `chat_messages` INSERT-only, the other six on `*` with `replica identity full` (without it RLS silently drops every UPDATE and DELETE event). ⚠ The client no longer spells the list — it comes from `REALTIME_TABLES` through `S.realtimeChanges()`, and `verify-066` pins the publication's membership equal to it. ⚠ `vote_ballots` is deliberately NOT published: 011 gives it a self-only SELECT policy, so Realtime would deliver each subscriber exactly their own ballot, and the tally lives in a VIEW, which a publication cannot carry — an open poll is refreshed by a 10-second poller instead. That is the anonymity decision, not an omission.

⚠ The same release fixes a defect only a fixture RICHER than production could hide: `CHAT_COLS` named six of the ten columns `chat_messages` has, so 附件 / @提及 / 引用 were written by `chat-send`, echoed to the sender's own screen, and **gone on the next load**. No suite caught it, because the harness fixture carried the four columns the client never asked for. `verify-066` now derives the ten names from the two migrations and requires `CHAT_COLS` to equal that set.

**Attachments and shares close the loop (§P1).** ⚠ A 配置包 sent to the room never had a card: `messageType()` recognised two kinds and `cmMsgHtml` drew two, so it arrived as a message with an attachment and nothing to press. The same vocabulary was spelled three times — `cloud_shares_kind_known` and `chat-send`'s `ATTACHMENT_KINDS` accepted two values while the picker drew three buttons — so 配置 + 聊天室 was a 400 behind a button the UI offered. There is now ONE list: `015` widens the constraint, `chat-send`'s `ATTACHMENT_KINDS` **is** `SHARE_KINDS`, and `messageType()` derives from it. `vote-create`'s `TARGET_KINDS` stays deliberately narrower (a poll attaches to a replay or a sample) but is derived too. ⚠ 「打开」 now really opens: a room attachment and a friend share go through ONE restore path (`cmImportShare` / `cmDoorFetch`) and a 配置包 reaches the real importer, instead of the sentence 「已打开：某名字（共 N 项）」 that lead nowhere. ⚠ A poll that fails to open is no longer reported as a failed SEND — the attachment is already in the room, and 「发送失败」 invites a second press. The room can 加载更多, through a real `before` bound rather than a second page of the newest.

**Messages and user settings (§P1).** A notice can be marked read individually (the button appears only while unread, and jumping to a message marks it on the way); 「我的举报」 lists what I filed and where it stands; the report form accepts an evidence JSON (parsed locally, so a typo is a sentence rather than a 400). 账号设置 gains 社区资料 — 隐藏我的国籍 and 在线状态, the options taken from the shared block's `MANUAL_STATUSES` so there can be no second answer. 登录 joins 激活 in the nav bar.

**⚠ The share quota becomes atomic (§P2).** 1.0.3 said the race was deliberately not fixed. 1.0.4 removes the LOST UPDATE without changing what the ceiling means: `claim_share_quota` / `release_share_quota` are one statement each (`insert … on conflict do update … where` under the cap), so the check and the write share a row lock. Both are `security definer` and granted to `service_role` alone — a caller who could execute `claim` would spend somebody else's allowance. ⚠ The release is deliberately asymmetric: the counter can end up one LOW (one extra share gets through — the pre-existing failure direction) and can never end up HIGH, which would lock a user out of their own allowance.

**i18n and acceptance.** 67 new strings across 13 locales, plus two dotted families (`cm.rst.*` for `REPORT_STATUSES`, `cm.act.*` for `ADMIN_ACTIONS`) registered in both places — an unregistered value prints as a raw `open` / `warn`. `verify-066` + `behave-066` join the sweep.

## 1.0.3

**§一 Community grows from one room into a set of social facilities.** Clicking an avatar opens a quick menu (访问主页 / 添加好友); the room can carry a replay or a sample as an attachment card with its poll underneath; `friendships` is one table with an ordered pair (`user_a < user_b`) plus two CHECKs — the requester is in the pair, and the block state agrees with `blocked_by` — supporting request / accept / decline / remark / remove / block / unblock. Friends can send replays (≤20/day) and configs (≤10/day), **the cloud copy lives 15 minutes**, and the recipient can either 打开 (fetch the summary) or 导入到本地 — the two are kept apart because a 15-minute clock is not a reason to write into somebody's sample library. There is no private chat: the 消息 page says to add them on gomoku instead.

⚠ **The quota is a read-then-write and the race is deliberately not fixed.** Two sends at the same instant can both read 19 and both write 20. That is accepted: the quota is a courtesy against a stuck retry loop, not a billing system, and the cost of the lost update is one extra share. Counting from `friend_shares` itself would be exact and need no counter — but §1.2.5 asks for this table and the client reads it to print 「今日还可发送 7 个」, and two sources for one number is the shape this project has already paid for six times.

**§1.4 Polls**: four choices (黑方 AI / 白方 AI / 双方 AI / 双方人类), 24 hours or closed by hand, one ballot per person. ⚠ **The anonymity is structural, not promised**: the tally is a view (`vote_tally`, `security_invoker = false`, emitting aggregate rows only) and my own ballot is read through a policy that admits only my row — so 「谁投了什么」 cannot be assembled at the database layer at all. ⚠ A poll only attaches to a **chat-room** share: `votes.target_cloud_id` references `cloud_shares`, which is the cloud copy `chat-send` creates for an attachment; a friend share is private and has no cloud copy at all, so the picker *disables* the vote box for a friend rather than hiding it, and says which of the two facts is the reason.

**§1.6/§1.7 Mentions and quotes**: right-click an avatar to insert a mention, or type `@` for an autocomplete whose candidates are your friends plus the room's current members — **minus yourself**, because a mention notifies every id in `mentioned_users` and notifying yourself is pure noise. Quoting a message auto-mentions its author (skipped when it is your own), and the quoted text is **snapshotted into the reply when it is sent**, so a quote whose original has been pruned still reads as it did rather than turning into a broken link.

⚠ **§1.8.3 read-only (P0)**: an unactivated account gets INTO the community and can READ it — §1.8.1's ✅ column — but every surface that writes is turned off: the room's input is disabled and says 「激活后参与讨论」, the 建议 submit button is inert, the avatar menu keeps 访问主页 and drops every 写 row, and the poll buttons plus the message right-click menu (mention / quote / report) are gone. ⚠ **The predicate is `users.activated_at is null`**, which is §1.8.2's own server-side spelling — and *not* `activationOpen()`. That one is shaped from the **session** (`stateOf` in auth.js calls a present, unexpired, unbanned token 「activated」 whatever `activated_at` says), so an account that registered but never entered a code sailed through the gate and got a live-looking room while every Function refused its sends with `NOT_ACTIVATED`: §1.8.3 shipped as **dead code** until a review of the gate found it. One predicate, `cmReadOnly()`, and every write surface asks it. ⚠ A **mute** is a different state and is deliberately not painted here: the client cannot know it (`muted_until` is on the caller's own row, not on anybody else's), so the refusal is the server's and it has its own `MUTED` branch.

**§二 Reports.** Submissions land in `reports` (four categories, up to 2000 characters of detail, optional evidence JSON); an administrator can warn / mute 24h / mute 7d / ban, and can also close the room or mute everyone through `global_settings`. ⚠ A mute is exactly one column, `users.muted_until`, with no `is_muted` flag: the predicate is 「is that moment still in the future」 rather than 「was it ever set」, so a mute lifts itself and nothing has to remember to clear it.

**§三 Country and presence.** The server derives a country code from the login IP (ipinfo.io; the key lives only in the Edge Function), the UI shows a flag emoji, **and Hong Kong / Macao / Taiwan map to 🇨🇳** — the real code is what is stored and the mapping happens in the display layer only (one implementation, `countryFlagChinaUnified`). There is a 隐藏国籍 switch. ⚠ `last_seen_at` is written only by `requireUser` as a side effect of any authenticated call, throttled by `PRESENCE_BEAT_MS`, and the client has **no** grant to write that column: a client that could write its own country and last-seen time would turn 「国籍」 and 「在线」 from observations into claims.

Presence uses Supabase Realtime Presence — a second hand-written Phoenix channel on its own socket, because the room's retry budget and fallback are tuned for 「a room that must keep updating」 and dragging presence into that fallback should not drag the room with it. ⚠ It degrades to the row-based answer, not to polling: `last_seen_at` is already the row answer, and a path with a row to read has nothing to poll. ⚠ The same `presenceState` reads both halves, so 隐身 means one thing in the room and the same thing on a profile page.

**Three architectural reversals.** (1) The client's readable columns are **narrowed**: `011` revokes the table-wide SELECT on `users` from `authenticated` and grants columns back. The `email` that would otherwise travel is not 「one fewer field」 — it is the privacy boundary itself. (2) `friendships` gains `blocked_by`: without it the blocked party could unblock themselves with `unblock` / `remove`, which would make §1.5.2's 拉黑 a suggestion; the freeze guard in `friend-accept` is that rule. (3) `quotaColumnFor` / `quotaMaxFor` move OUT of 「server only」 and into the shared block: the share picker has to print 「今日还可发送 N 个」 for the kind about to be sent, and `shareQuota()` deliberately returns the two counters rather than a per-kind answer, so which counter a kind spends has to be one answer on both sides.

**Caught by our own rules again.** ⚠ **Ten new error codes re-prove 「create a code, then give it a message branch」** — `MUTED`, `CHAT_DISABLED`, `SHARE_EXPIRED`, `QUOTA_EXCEEDED`, `FRIEND_EXISTS`, `NOT_FRIENDS`, `BLOCKED_BY_USER`, `VOTE_CLOSED`, `VOTE_ALREADY_CAST`, `TARGET_NOT_FOUND` all have `cloudErrText` branches, with the fallback left last. ⚠ And `verify-064`'s 「exactly three secondary tabs」 went red the moment this version added two more — the defect it guards is a tab being **deleted**, not one being **added** — so it is now a floor plus the three names, and the exact inventory belongs to `verify-065` alone.

**§一 The activation gate gives one panel back.** 1.0.1 locked eleven settings panels; 1.0.2 frees 语言与显示, so an unactivated operator can now reach 云账户与同步 / 语言与显示 / 新手教程 / 关于 — four panels — plus the 标签介绍 modal (标签百科), which hangs off a button inside the open 新手教程 panel rather than being a panel of its own. ⚠ **This change unearthed a real bug in the i18n toolchain.** `keys.cjs` registered *every* `'key': 'value'` line in `zh-CN.js` as a semantic key, and semantic keys (a) take priority over the `html|` implicit keys and (b) are skipped when the twelve tables are generated. So adding the one override row `zh-CN` needs — the only row in that file whose key contains a `|` — would have **silently deleted that row from all twelve generated tables**, and `--check` would have said nothing, because it compares whether the inventory is *complete*, not whether it is *correct*. ⚠ **Reads and writes take deliberately different routes.** The write half goes **only** through Edge Functions, and `005_community.sql` contains **no client INSERT policy at all**. This is not fastidiousness: §2.3.5's two protections are 「at most 10 messages per minute」 and a blocklist, and a Postgres policy can neither count a stranger's rows over the last minute nor read a word list. Shipping a client INSERT policy would demote both to decoration — one edit in a console and they are gone, while the server goes on accepting everything. The read half keeps going through PostgREST + RLS, so the push subscription and the list are authorised by the *same* policies: one authority, not two. For the same reason `news_read` is `is_activated()` rather than §2.4.3's `using (true)` — §2.1's rule is the newer instruction, and the migration says so in a comment rather than hiding the fork.

The client copy says in its own header that it is there to fail fast, not to be authoritative: no table has a client write policy, so editing it in a console accomplishes nothing. §2.4.4's translation fallback (requested language → original → 「原文（xx）」) lives in the same block, for the same reason the limits do — two callers each writing half of a fallback chain is how they start disagreeing.

**This release reverses one of 1.0.0's headline promises, and that is deliberate.** 1.0.0's 「老用户不锁死」 said core detection — capture, analysis, archives, the sample library, the learning loop, the blacklist — stays free and purely local forever. 1.0.1 says **未激活无法使用大部分功能**: as an unactivated operator you can still paste a game record into the viewer and run the global analysis, use the AI thinking panel, and export JSON / CSV / print, plus one-click update and the tag wiki. What you cannot do is accumulate data or monitor a game live — no overlay (not hidden, **not created at all**), no replay, no sample library, no blacklist, and no 设置 · 其他 panels.

**The gate is one predicate and it reads the markup, not a list.** `GMAuth.gateOpen()` is the only answer to 「是否准入」, asked by four surfaces: the content script, the viewer's nav routing, the viewer's settings panels, and the account area. A second spelling is how four surfaces end up disagreeing about the same operator, which is why `content.js`'s copy defers to the module and comments that a missing module is a bug rather than a product state. ⚠ **One spec fork needed the operator, and 「没后端就不拦」 is what was chosen.** §1.2's pseudocode returns early when the operator is not activated, which on a build with **no backend** would brick the tool: no server means no code issuer, so nobody could ever activate and 「暂不」 would be a door that does not open. `gateOpen()` therefore answers `true` when `isConfigured()` is false. A room with no door does not need a key.

⚠ **「出厂状态」 changed meaning, and the acceptance suite says so in words.** 1.0.0 §十三 told the operator to paste their own URL and keys, so 「what ships is two empty string constants, and no call touches the network」 was a true assertion. **1.0.1 reverses it, confirmed with the operator:** §1.4's model (read the session, inspect `exp`) has no `isConfigured()` layer at all, and §1.5's six acceptance criteria are not even statable against a backend-less build — with no server there is no code issuer, so nobody can activate and the whole gate is dead code. The operator's two commits pointing the extension at the production project match that intent. So `verify-062` §1 moved from 「占位符为空」 to 「指向一个托管的 Supabase 项目」 — and the coverage for §1.2's promise was **not** dropped: the literals are now emptied explicitly and every account-aware entry point is asserted to answer `NOT_CONFIGURED` without reaching the transport. More coverage than before, not less.

**Two-step registration, with Resend for the mail.** 1.0.0 was 输码即建号. 1.0.1 splits it: `auth-validate-code` answers 「can this code be used?」 — a **query**, HTTP 200 with `{valid, reason}` where the reason is `NOT_FOUND` / `REVOKED` / `ALREADY_USED`, because 「this code does not exist」 is a normal answer to 「can this code be used」 rather than a transport failure — and only then does the registration window open, with five fields, a strength bar, a 60-second resend cooldown and live username-uniqueness probes. §2.3's rules are at least 8 characters with letters **and** digits, no case requirement; 确认密码 is front-end only and is never sent. Eight new Edge Functions, one new `email_codes` table with **RLS on and no policy** (so a leaked anon key cannot read anyone's code), and `users.token_epoch`.

⚠ **「撤销所有设备 JWT」 is an epoch column, because a JWT cannot be unsigned.** §3.7 requires a password change to sign out every device, so the counter is minted into the token's claims and `requireUser` rejects a mismatch. Changing a password or resetting one bumps it; changing an email does **not** — an email change is not a revocation.

⚠ **`requireUser` now verifies the signature itself instead of calling GoTrue's `getUser()`.** `getUser()` also looks the `sub` up in `auth.users`, and 1.0.0's `auth-activate` minted tokens for users who have a `public.users` row and **no GoTrue identity** — so the original code would have handed exactly the population 1.0.1 promises not to lock out a 401 on every `profile-*` and `auth-change-*` call. GoTrue stays the credential authority (it judges passwords); the session is always our own `signJwt`, because a GoTrue token carries no `epoch` and would be rejected by the revocation check above.

⚠ **Two places where the spec's example and its formula disagree, and the formula wins** (the standing rule: implement the formula, write the disagreement down). §2.4's sample generates the six digits with `Math.random()`, which is biased and not cryptographically secure; the requirement is 「6 位数字」, so the code ships on `crypto.getRandomValues` with rejection sampling. ## 1.0.0

**This is a productisation release, not a detection release.** 1.0.0 turns 白身 (Baishen) from a purely local extension into a product with an account system — 「云账号 + 激活码 + 管理员」 — and the fifteen detection increments underneath it are unchanged. Every one of the eleven architecture decisions in the 定稿's 零 section adopted the recommended option, and the three that shape the rest of the release are: **老用户不锁死**, **云同步默认关闭**, and **Service Role Key 绝不进扩展**.

**The shipped state has no backend, and that is a feature.** §十三 tells the operator to supply the Supabase URL and keys themselves, so what ships is `cloud.js` with two empty string constants. In that state `isConfigured()` is false, every call resolves to `NOT_CONFIGURED` **without touching the network**, and every account-aware entry point degrades rather than throwing — so a 0.5.x operator who never types an activation code sees exactly the extension they had, minus two nav buttons. That is §1.2's 「不破坏已有用户的本地使用」 implemented literally, and it is the first thing the new suite drives, in both configurations.

**Activation.** Codes are `BS-XXXX-XXXX-XXXX-XXXX`, sixteen Base32 characters with the confusable `I/O/0/1` removed. One code per account is enforced by a partial unique index (`idx_code_redeemed`) plus an optimistic lock on the bind (`update … where redeemed_by is null`), not by a read-then-write — two clients racing the same code is the normal case, not an edge case. JWT is 30 days, renewed every 7; the offline grace window is 30 days, and the four states (`none` / `active` / `grace` / `locked`, with `banned` outranking all of them) are a pure function of `(session, now)` so they can be tested without waiting a month. §0 #2's three-device ceiling and §3.6's bulk revocation are both server-side.

⚠ **Two spec facts disagree with the spec's own examples, and the examples win** — the standing rule of this project is to implement the formula and write the disagreement down, and this release has three of them. §3.1's prose says the code is 「总长度 23 字符」 while its pattern in the same section is **22** (`BS-` + 16 + 3 hyphens); the pattern is what the Edge Function generates and what the server compares, so 22 ships. §4.4's `compressAvatar` sample *stretches* an image to 256×256 while §0 #9 says 压缩到 256×256, so the implementation centre-crops then scales, which is the reading that does not distort faces. And §8.2 defines obfuscation configs `heavy` and `light` while §8.1's file table — the table that actually assigns the files — marks four of them **中度**, and §8.2's own strategy map refers to `'medium'`; there is no `medium` in §8.2, so this release defines it as the tier between the two and records that here rather than quietly picking whichever was easier.

**Cloud.** Three migrations and twelve Edge Functions. `001_init.sql` creates `users` / `activation_codes` / `devices` / `samples` / `archives` / `badges` plus the `updated_at` triggers §7.3 compares on; `002_rls.sql` turns RLS on for every one of them and writes the policies, default-deny; **`003_user_kv.sql` fills a real gap** — §7.2 names four sync categories (黑名单 / 设置 / 自定义问题 / 学习参数) and §11.1 gives a table to none of them, so `user_kv` holds them with the `key` column **whitelisted** rather than free text, because a free-form key would be a second place to store per-user data that RLS cannot reason about. The security boundary is §2.2's: the anon key is public and is designed to ship; the service-role key is read from `Deno.env` inside the functions and appears nowhere in the extension, which the suite asserts script by script. Administrator status is decided **only** server-side — the client's `GMAdmin.isAdmin()` gates a *tab* and nothing else.

**Client.** Five new modules. `cloud.js` is the single network door and the single answer to 「is there a backend」. `auth.js` owns activation, the session, renewal and the state clock. `profile.js` owns §5.3's one `profile-get` call and §4.4's avatar pipeline. `sync.js` owns §7.2's eight rows, §7.3's `updated_at` comparison and §7.4's retry queue. `admin.js` owns §6.2's operations, each guarded by one `guard()` and each backed by a named Edge Function that re-verifies the admin flag. `storage.js` gains `cloudSession` / `deviceId` / `syncQueue` — and the session is deliberately kept **outside** `settings`, because a backup file is a thing people mail to each other: putting the JWT inside the backed-up object would leak it *by construction*, which no amount of remembering to `delete` it afterwards would fix.

**Obfuscation (§八).** `javascript-obfuscator` behind a three-tier per-file strategy: `app.js` and `learn.js` heavy, 开局表 / 数据结构 / 翻译表 / 站点配置 medium, UI and page-communication light. `hook.js`, `worker.js` and `manifest.json` are **absent from the strategy map entirely** — they are the MAIN-world entry, an `importScripts` path and a file Chrome reads before our code runs, so "unobfuscated" is a stronger statement than a level could make. The MV3 constraints are hard gates, not preferences: rc4 encoding, `selfDefending` and `debugProtection` are off (the first costs measurable CPU per hand; the other two synthesise function bodies the MV3 CSP forbids), `renameGlobals: false` and `disableConsoleOutput: false` stay, and the build asserts on its *output* that no `eval`/`new Function` survived and that no `chrome.runtime.onMessage` type string was renamed — a renamed message type does not fail to compile, it silently does nothing. **Honest note, per §8.5: Rapfi is open source, so obfuscation protects the post-processing (the `sideAggregate` / `classifySide` family) and nothing above it. It is a raised bar, not a security boundary.**

**Privacy (§九).** `PRIVACY.md` is the source of truth, bilingual, with §9.1's table: what is uploaded (username, email, avatar, sample *metadata*, activation state, device ID), what is **not** (game records, detection results, local settings and the blacklist unless cloud sync is explicitly enabled), where it lives (a Supabase region, Singapore recommended), retention (30 days after deletion), and the user's rights. `docs/privacy.html` is the zero-external-resource page to host on GitHub Pages; `docs/DEPLOY.md` answers §十三's three open questions, including how to mark the first administrator with a one-shot `update users set is_admin = true`.

**Acceptance.** `verify-062` is the new newest suite and therefore the only one holding the exact `1.0.0` pin; it drives the unconfigured and configured halves separately, walks §3.4's state table at fixed timestamps, and checks that every new `T('viewer|…')` literal has a twelve-language row. `verify-061` gives up its exact pin — and, with it, the live-`releaseNotes` content assertions, which can only ever be green for one release and have now gone red on this project three times.

## 0.5.7-Alpha

0.5.7-Alpha corrects the regression 0.5.7 shipped, and it is the second release in a row whose headline change is subtraction. 0.5.7 added three signals for the low-end cheater and raised the ceiling to 150% to pay for them; measured on the operator's own corpus, the largest of the three was inflating an ordinary human's score by about five points — not because those humans played like an engine, but because the thing the signal measured is decided by the rules of gomoku rather than by the player. The ceiling, the three keys and the 低端AI class all stay. Two of the three signals are re-pointed and then **zeroed**, and the weight they free is moved. The version is **0.5.7.1** and not the spec's `0.5.7-Alpha`: Chrome's manifest takes one to four dot-separated integers, and this extension's own `compareVersion()` splits on `.` and `parseInt`s each segment, so `parseInt('7-Alpha', 10) === 7` and an installed 0.5.7 would never have seen an update. Alpha lives in the prose and the commit message, nowhere a version is compared.

**不漏防 was reading a rule, not a player (P0).** 0.5.7's flag was "this hand answered a 冲四 that had exactly one blocking point", and the activation rewarded never missing one. But a 冲四 has exactly one completing point **by construction**, so "exactly one defence" is a property of the shape and every player who can count to five blocks it — human or machine, in every game, at every level. The signal was therefore ≈1 nearly everywhere: re-scored over the operator's **65 archives / 127 scored sides**, it was non-zero on **54%** of sides and paid **+5.29** points on the average one, which is where the ≈5-point inflation came from. A term that is constant across both groups carries no information and still spends its 15% in every score, which is the worst of both.

**The direction moves from 堵冲四 to 防四三杀, and the fix is a new function rather than a rewrite (§3.2).** §3.2 proposed re-pointing `uniqueDefences` at the 四三杀 threat. That function has two production callers — 0.4.8's 被迫防守豁免 (`forcedDefenseByShape`) and 0.5.0's 四三杀反制检查 (`uniqueBlocksForFour` → `checkFourThreeCounter`) — and changing what it returns would have changed both silently, so the new predicate ships as **`fourThreeDefences(board, side)`** and `uniqueDefences` is untouched. The threat it encodes is the one §2.2 describes: the opponent holds **both** a four (冲四 or 活四) and an open three at once, so blocking the four does not answer the three and blocking the three does not answer the four. The defence set is enumerated off the board, never off the engine's candidate list, and a position the side cannot save yields an empty set rather than a counted miss. The sample factor is unchanged from 0.5.7 — `clamp(base × min(1, n / NO_BLUNDER_MIN), 0, 1)` with `NO_BLUNDER_MIN = 3` — but it now binds on essentially every side, which is the finding below rather than a design choice.

⚠ §3.1's pseudocode and §2.2/§2.3's prose disagree about what counts as a defence, and the disagreement is load-bearing. §3.1 clears the threat when the move removes **either** half — the four or the live three; §2.3's 「防守点集为空时不计入统计」 and its 「只堵四」 example both presuppose a set that can be empty, which only the stricter 「must clear both」 reading ever produces. Measured over the corpus, the strict reading returns an empty set on **13% of sides (16 hands)** and the pseudocode's reading never does: under the pseudocode a 四三杀 always has at least one point that breaks it, so §2.3's sentence is dead code and 「只堵四」 — the exact play §1.3's motivation is about — scores as a success. **The pseudocode is what ships**, taken knowingly with that sentence left inert, because the alternative contradicts §3.1 and would silently re-classify one side in eight as "no defence available".

**Re-pointed, the trigger is too sparse to carry anything, so the weight goes to 0 (§七.2 is unreachable).** 「对手同时持有一个四和一个活三」 turns out to be rare: over the corpus's **1084 analysed hands** it occurs on **24 hands (2.21%)**, and only **16%** of sides ever see it at all. **No side in the corpus reaches `NO_BLUNDER_MIN = 3` occurrences**, so the sample factor never leaves the ground and the activation is **0.051 on human sides and 0.055 on machine sides**. Re-pointing the signal therefore fixed the false positive without creating a true one: it is no longer wrong, and it is no longer anything. §七.2's acceptance criterion 「AI 玩家 aNoBlunder ≥ 0.50」 is unreachable under **either** reading of the defence set, and no allocation of weights can reach it. So **the weight is 0**, handled exactly like `time` in 0.5.7: the key, the panel row, the formula and the probe library all stay, and only the number is zero. It becomes live again the day a corpus can trigger it.

**探针匹配 is re-pointed to the same motif, then zeroed for the same reason (§3.4).** §3.4 asks for the probe library to be rebuilt around the 四三杀 shape rather than the 冲四 shape — a four on one line plus an `_XXX_` open three on a second, independent line, with the expected move still the four's blocking point. `probes.js` is rewritten to exactly that: **ten canonical motifs × eight symmetries = 80 oriented probes**, the same canonical and oriented counts as before, and every probe is materialised from its own definition and re-matched in the suite (**420 legal placements, 0 failures**, and blocking either end of the three correctly stops the match). The structure survives; the coverage does not. 「本方持有一个四和一个活三」 — the attacker-side motif the probes encode — occurs on **0.38% of hands (4 of 1040)**, against **15%** for the 冲四 library it replaces. After the swap the probe almost never fires, so `probeMatch` is a constant 0 and its 0.12 is zeroed alongside `noBlunder`'s 0.15. ⚠ §3.4's stated rationale for the swap was that the probe and 不漏防 would then measure the same thing — 「与 noBlunder 同源」 — and that rationale evaporates the moment `noBlunder` is zeroed. The swap is kept anyway, as the operator's decision, and recorded here so a later reader does not mistake it for an accident.

**The freed weight is moved, and 0.21 of it is parked (§四, deepened by measurement).** The two retired terms free **0.27**; `out` gives up **0.15** more (0.27 → **0.12**), for **0.42** to place. Of that, **0.16** goes to `goodPool` (0.03 → **0.19**), **0.03** to `top1` (0.20 → **0.23**) and **0.02** to `acpl` (0.08 → **0.10**), and the remaining **0.21** is parked on the five behaviour terms that measure exactly zero on this corpus — `desperate`, `evasion`, `uselessFour`, `sharpStreak`, `sharpTotal`, each roughly ×1.5 to ×2 — because the table must still close at exactly **1.50** (§七.7) and measurement says a point given to any term that is *alive* here raises the mean by 4–16 points and cancels the drop the zeroes just bought. The parking is arithmetic, not a fit: those five terms are live on other corpora (real evasions, real 无用冲四, real 唯一手 runs), so the weight is not wasted, but their values are a place to stand rather than a measurement. `out`'s cut is deeper than §四's −0.10 because it is the **only** knob that moves the ≥70 line: a machine side's `out` activation is **0.891** against a human side's **0.097**, where `goodPool` is **0.566 / 0.304** — `goodPool` lifts everyone, `out` moves the tail. Doing §四's −0.10 literally made the ≥70 share *rise* by 4.7 points. The largest single term in the table is therefore no longer 出前五 at 0.27; it is **命中率 `top1` at 0.23**, and the wiki's 「最大的一项」 claim moves with it.

**Measured, table against table.** Re-scored over the same 65 archives / 127 scored sides, comparing the 0.5.7 table read with the 0.5.7 activations against the new table read with the new ones — the archives predate 0.5.7, so their stored `risk` is not a 0.5.7 score and cannot serve as the baseline: average side **56.81 → 48.06**, **−6.77** on human sides and **−11.34** on machine sides; the share at or above **70** falls **23% → 15%**, i.e. **−7.9 points**. Both sit inside §七.3's bands (−5~−8 on the human mean, −5~−10 on the ≥70 share). Two of §七's criteria are **not** met, and both are structural rather than tuning failures. §七.2's 「AI 玩家 aNoBlunder ≥ 0.50」 is unreachable because the trigger is too rare, as above. §七.3's 「≥40 比例保持稳定」 is unreachable in **any** allocation: zeroing two terms removes about twelve flat points from every side, so the whole distribution shifts down and the 40 line necessarily loses 12–18 points — it measures **75% → 63%, −11.8 points**. A grid search over 42 tables and a 24-configuration "leave headroom" scan produced no configuration satisfying all three sub-criteria at once. The cause is that §七.7's 「合计精确 1.50」 and §七.3's 「均分 −5~−8」 pull against each other: spend the whole 0.27 on live terms and the mean can only fall 1–5 points; leave the total short and the 1.50 invariant breaks. Parking is how this table satisfies both.

**Two things measured backwards, and left alone.** 败势不崩 `steadyLost` scores **higher on human sides (0.606) than on machine sides (0.344)** — the opposite of its intent. The cause is the corpus, not the curve: the sides the detector calls AI tend to be *winning*, so they rarely sit in a `bestWR < 0.20` position and never accumulate the sample the term needs, while a human side that is losing steadily collects it. The definition is unchanged and its weight is unchanged at 0.08; only the reading is recorded. And a caveat that applies to every "which term discriminates" figure in this entry: the corpus's `types` labels are **the detector's own verdicts**, not ground truth, so the discrimination measured here is measured against the thing being changed. It is the best evidence available on this corpus, and it is not independent evidence.

**The three mirrors and the learner move together.** `BASE_WEIGHTS` (app.js), `DEFAULT_WEIGHTS` (storage.js) and `FALLBACK_WEIGHTS` (learn.js) all carry the same sixteen values and all total exactly **1.500000000000**; no mirror differs. The learner reads its two budgets off the defaults rather than holding a second copy, so zeroing two keys moved the split from **0.85 / 0.65** (six statistics / seven behaviour signals) to **0.79 / 0.71** — and the low-end group, `['noBlunder', 'steadyLost', 'probeMatch']`, now holds a single live term worth 0.08. The 0.02 AUC floor in `group()` reads the *default* weight, so a key whose default is 0 gets no share, which is what keeps `noBlunder` and `probeMatch` — like `time` — switched off after a training run.

## 0.5.7

0.5.7 raises the weight ceiling to **150%**, retires the time signal, and adds three signals for a cheater the detector had no way to see: one who relays every move through a shallow web engine's strongest level. It also washes the whole overlay red for the duration of a blacklist alert.

**权重上限 150% 与低端 AI 检测（P0）.** `SIGNAL_WEIGHT_SUM_MAX` moves from 1.30 to **1.50**, and the shipped table spends it: sixteen terms totalling exactly 1.50. `time` goes from 15% to **0%** — the field stays in the table and in storage so a pre-0.5.7 archive still describes itself, but it no longer scores, because the cheater this release is about does not think; they copy, and the interval between two copied moves is the interval between two clicks. Three terms are added, and they are the **first** in this detector that are not derived from the engine's candidate list at all: 不漏防 `noBlunder` **15%**, 败势不崩 `steadyLost` **8%**, 探针匹配 `probeMatch` **12%**.

不漏防 is the simplest of the three and the one that matters most. A forced defence is a hand where the opponent left exactly one point that answers a 冲四, and the flag is stamped per hand by `scoreStep()` from the board before the hand — `uniqueDefences(board, side)` returns the threat's kind (`'four'` or `'openThree'`) and the points that clear it, and a hand is a threat when that list has exactly one entry. A side that never misses one is not a side that had to think: a shallow search one ply deep finds the block by construction, while a human under time pressure does not. 败势不崩 reads the stored win rate and the loss of the hands already in a lost position (`bestWR < 0.20`): a shallow engine's evaluation is stable, so a lost position stays lost in an orderly way instead of collapsing into flailing. 探针匹配 is the third, and §1.3③'s own finding is recorded below rather than papered over.

§1.5 adds a fourth AI class, **低端AI** (`type: 'lowEndAi'`). The three strong bands are all built from terms that ask "how close was this to a STRONG engine's own choice" — `top1`, `sharp`, `out`, `goodPool` — and a shallow engine's choices are not a strong engine's, so the cheater lands in 职业选手 / 高手玩家 rather than 疑似AI. What such a side *can* satisfy is the two new board-and-composure terms, because it searches at least one ply and its evaluation is stable. So a side whose score lands in 职业选手 or 高手玩家 while `noBlunder > 0.8` **and** `steadyLost > 0.7` is downgraded to 低端AI and handled as 疑似AI. The two cuts are on the ACTIVATIONS, not on the points, so the rule does not move when the weights are rebalanced.

The sample floors are the one place this release deliberately departs from the 定稿's literal formula, and the departure is documented in `app.js` beside the code. The spec's `≥3` gate makes its own threshold inert — `1 - 0/1` is already 1, so a side that faced a single threat and blocked it would be handed the full 15% — while a hard floor (`< 3 ⇒ 0`) both discards real evidence and inverts the order, scoring a 2-threat/0-miss side below a 4-threat/2-miss one. What ships is the sample-scaled reading, `clamp(base × min(1, n/threshold), 0, 1)`: spec-exact at n ≥ 3, monotone below it, and measured rather than argued.

**探针匹配 sits on the same measurement as 不漏防, and that is a finding rather than a bug（§1.3③）.** §1.3③ names three probe families. Measured against what the detector can actually decide, only 唯一防守点 is encodable: its motif is "four `T` stones in a clear 5-cell window", i.e. a 冲四, and the machine's move is the window's one empty cell. But every 冲四 has exactly one blocking point — so §1.3③'s family ① *is* §1.3①'s threat. Counted per hand over the operator's own **65 archives / 1084 analysed hands**: `probeSeen` and `oppThreat` both fire on **164**, probe-only on **3** (a 活四 window, a motif with no forced block), threat-only on **0**, and of the 164 the two agree about the move **164 / 164**. The 12% and the 15% therefore sit on one measurement — **0.27 of the 1.50 ceiling is spent on a single signal** — and the release notes say so rather than presenting the probe as independent evidence. The other two families (双威胁选择, 败势顽抗) are **not** encodable and are not encoded: their `expectedMachine` is a property of a specific web engine at some search depth, not a property of the board, and any value invented here would be a guess wearing the costume of data. They become encodable the day someone records one. `probes.js` holds what is encodable: **ten canonical shapes** (five gap positions along `x` **and** the same five along the diagonal — the eight square-lattice symmetries never map an axis to a diagonal) × eight symmetries = **80 oriented probes**. Coverage over the corpus is **167 of 1084 hands (15%)** where the axis-only library reached 90 (8%); 1.31 probe positions per side, 44% of sides see none, 18% see three or more, and the hit rate where a probe occurs is 95%.

Re-scored over the same **65 archives / 127 scored sides**, the net effect of the three new terms and the retired one is **+1.08** on the average side (**49.52 → 50.60**), and the distribution moves the way the increment intends: sides at or above **70** fall from **35% to 20%**, while sides at or above **40** rise from **52% to 59%**. Roughly half the sides move up and half move down, which is what "one 15% term retired and three worth 35% added, with the base six untouched" should look like. Per term: `time` was paying **8.15 points** on the average side, 不漏防 adds **5.29** and is non-zero on **54%** of sides, 败势不崩 adds **3.94** and is non-zero on **61%**.

**黑名单浮层背景同步闪烁（P0）.** A blacklist alert used to flash only the panel's border. Now the whole overlay background flashes with it: a `.gm::after` pseudo-element at `inset: 0` with `pointer-events: none` and `z-index: 0`, animated by the `gm-bg-flash-blacklist` keyframe — `opacity` 0 → 0.22 → 0 over 0.3 s × 3, in the same red the border keyframe pulses to. Two details are deliberate. It is `::after` and not `::before`, because `::before` is the background image's scrim and must keep its own stacking; and when a background image is set, the wash paints **above the picture but below the content** (both sit at z-index 0 and `::after` comes later in paint order, while the `.has-bg` block lifts the children to z-index 1), so the picture is washed red for the duration and is untouched the moment the opacity returns to 0. Two corrections to §2.2's own CSS are recorded in `content.js`: the sketch sets `background: rgba(255,59,48,.22)` **and** ramps `opacity` to 0.22, and the two multiply, so the brightest frame composites to ≈4.8% and the flash is invisible on a dark panel — the colour is opaque `#ff3b30` here and the keyframe carries the whole 0.22; and §2.2's `:host(.has-bg) .gm > *{position:relative;z-index:1}` must **not** be added, because `.gm > *` already carries the z-index and the `position` half would turn `.rz` — the resize handle, `position: absolute` — into a static box. No JavaScript changed: `triggerBlacklistAlert` already routes through `playFlash` → `setBorderState(next)`, and the CSS is scoped to `data-bs="blacklist"`, so the pseudo-element loses both its animation and its background the moment the border is handed back. The 1 s `FLASH_MS['blacklist']` timer stays as the belt for a lost `animationend`.

## 0.5.6

0.5.6 makes everything stored locally portable — one JSON file, nine selectable categories, and a per-item rollback on the way back in — and rebalances the score so the behaviour signals, not the base statistics, carry the majority of it.

**导出与导入（P1 导出 / P0 导入退回）.** The eight categories the profile actually holds are now selectable one by one and written to a single `baishen-backup-<Beijing timestamp>.json`: settings, 黑名单, 样本库, 回放存档, 自定义问题, 自定义引擎（元数据）, 学习参数, 背景图片 and 列折叠偏好. Three things are deliberately NOT in the file, and each for its own reason: `apiKey` never leaves the machine, because a backup is a thing people hand to each other; the custom engines' weight packages do not, because they are up to 100 MB each and an `apiKey`-free inventory row is all the receiving machine can use anyway; and `updateInfo` does not, because it is a transient record of a check that has already happened. The envelope carries `kind`, a format `version`, `exportedAt` and `appVersion`, and a file from a newer build is accepted with a warning rather than refused. On import nothing is written until the operator confirms: the file is parsed, its `kind` checked, and a dialog then lists **the file's own** categories with their counts, everything ticked. Import is not the reverse of export — it is a decision. Settings, 学习参数, 背景图片 and 列折叠偏好 overwrite; 黑名单, 样本库, 回放存档 and 自定义问题 append, with a clashing ID skipped for the block list (importing someone's block list should not silently re-edit the entries already here) and given a fresh one for the rest, exactly as the manual importers have done since 0.3.4.

The one rule worth stating on its own is what happens to a value this device cannot honour. A backup made on a 16-thread machine, imported onto an 8-thread one, does **not** get clamped to 8: the thread count, `minArchiveMoves`, `openingCutoff`, `thinkMs`, `aiThinkMs`, the language, the four enum settings, every field of both transparency panels, `archiveFilter`, `storageFilter` and `engineId` are each checked against the ceiling that actually applies here, and a value that fails keeps the **pre-import** value and is reported. A clamp would store 8 without a word and leave the operator believing the machine now runs 16. `engineId` is the one exception, and it falls back rather than rolling back — to Rapfi, because an engine id nothing answers to leaves the detector unable to search at all. Every refusal is reported with both numbers — what the file asked for and what is still in force — and the report closes with the per-category counts: successful, rolled back, skipped, and why. The counts that arrive as junk are counted rather than thrown: a block-list row with no `id`, a sample with no moves, an archive with no `record.moves`, a background whose `blob` is not a data URL.

**权重调整（P0）.** The score is summed from thirteen terms whose total had been 1.00 since 0.5.5; this increment moved the split, not the total. Five terms were named: 回避手 `evasion` 0.04 → **0.08**, 唯一手连续 `sharpStreak` 0.03 → **0.14**, 唯一手累计 `sharpTotal` 0.03 → **0.18**, 好点池 `goodPool` 0.18 → **0.21** and 活三好手 `liveThree` 0.03 → **0.06**, together 0.67 where they were 0.31. The other eight therefore shrink by proportion — 0.69 → 0.33, a factor of ≈0.4783 — and the direction is the whole point: `sharpStreak + sharpTotal + goodPool` came to **0.53**, over half the budget, where the four base terms `top1 + acpl + sharp + out` came to 0.23. The score reads behaviour first and statistics second, which is what those five terms exist to express. `BASE_WEIGHTS` (app.js), `DEFAULT_WEIGHTS` (storage.js) and `FALLBACK_WEIGHTS` (learn.js) move together, and the learner's two budgets follow from the defaults rather than from a second edit — the six statistics normalised against 0.30 and the seven behaviour signals against 0.70, where 0.5.5 had them at 0.63 and 0.37. 标签百科 prints each signal's weight by reading it live, so its figures follow automatically; the prose that still described the 0.5.2 surcharge model was the only part that had to be corrected. ⚠ **This paragraph is the record of an intermediate state**: later in the same release 补增 §三 replaced the whole table with the operator's own, whose total is **1.236** (see the next paragraph), so none of the numbers above are the shipped table any more.

**Per-signal weights (P1).** The settings page gains a 检测信号权重 panel: one percentage box for each of the thirteen detection signals, so the operator can write the table themselves. Only the signals that differ from the one they inherit are stored, which keeps a later release's rebalance reaching the terms nobody touched, and clearing a box restores that signal's default. The total is capped at **130%** and it is printed above the grid as 「合计 x% · 上限 130%」, turning red the moment the boxes are over it. An edit that would cross the ceiling is refused rather than trimmed, and the refusal names both numbers; storage.js, the import validator and the analysis path all apply the same rule, so a profile, a backup and a running analysis cannot disagree about which table is in force, and an imported table over the ceiling is rolled back rather than quietly rescaled. The weights are **absolute**, not shares renormalised back to 1.00, and that is what makes the ceiling statable at all: under a 1.00-normalising rule, lifting all thirteen signals by 1.2 would do precisely nothing. 标签百科 prints each signal's figure by reading the live table, so its numbers follow the operator's own table too.

The operator then went one step further and confirmed that **the table they had tuned is the table this release ships**. So `BASE_WEIGHTS` / `DEFAULT_WEIGHTS` / `FALLBACK_WEIGHTS` are now their numbers — `top1 13% acpl 7% sharp 13% out 11% desperate 4% time 10%`, then `evasion 4% winBlunder 3% uselessFour 4% sharpStreak 14% sharpTotal 18% goodPool 19% liveThree 10%` — totalling **1.30, which is exactly the ceiling** where every release since 0.5.5 had totalled 1.00. An untouched install therefore scores **30% higher** than it did, with the 70 / 40 lines unmoved — a deliberately stricter detector out of the box, which is what the operator asked for, and the panel prints the total next to the boxes so nobody has to infer it. A total *below* the shipped one is allowed as well and means the opposite. The learner's two budgets are read off the table, so they moved with it: 0.58 for the six statistics and 0.72 for the seven behaviour signals. ⚠ **This table was itself replaced later in the same release** — see the 后续 paragraph below, which is the table this build actually ships. One consequence is worth stating plainly, because it is arithmetic rather than a defect: **the shipped table spends the whole ceiling, so it leaves no headroom.** A profile that raises one signal without lowering another is refused — the panel turns the total red while the number is typed and declines to save it — and the way to give a signal more weight is to take it out of a different one first (「先降一项再抬另一项」). 好点池 was, at that point, the largest single term at 0.19 — by one point over 唯一手累计 at 0.18; the paragraph below moves that claim to `out`.

**补增 §三 后续：the table goes back to 0.5.3's shape (P0).** The ceiling and the rule above are unchanged; what changed is which terms the weight sits on, and the reason is a measurement rather than an opinion. Re-scored over the operator's own **65 archives / 127 scored sides**, 补增 §三's table produced an average side of **36.8** where 0.5.3's produced **46.9** — the total was the same 1.30 both times, so the whole ten-point drop was composition. The cause is where the weight had been moved to: 唯一手累计 (0.18) and 唯一手连击 (0.14) almost never fire, and **34% of that table — 0.44 of 1.30 — scored zero in every one of the 127 sides**, with 绝望手, 规避 and 无用冲四 joining them. The six base statistics, which are what actually pays (42.9 of the 46.9 points an average 0.5.3 side scored), had been cut from 1.00 to 0.58 to make room for them. So the six are 0.5.3's own numbers again — `top1 20% acpl 8% sharp 22% out 27% desperate 8% time 15%`, together **1.00** — and the seven behaviour signals are 0.5.3's seven (`6/4/5/4/3/3/3`, together 0.28) scaled ×30/28 so the table closes at exactly **1.30**, the ceiling: `evasion 7% winBlunder 4% uselessFour 6% sharpStreak 4% sharpTotal 3% goodPool 3% liveThree 3%`. The largest single term is 掉出前5 (`out`) at 27%, as it was in 0.5.3; 好点池 is back to 3%. The three mirrors move together as before, the learner's two budgets follow the table (1.00 for the six, 0.30 for the seven), and 标签百科's 「最大的一项」 claim moved from 好点池 to `out` with it. ⚠ This is a revert of composition, not of mechanism: a pin still may not raise a term, because the shipped table still spends the whole ceiling.

**无用冲四 never scored, because the field it is read from was never written (P0).** `markFourRuns` groups each side's consecutive fours into runs and labels them VCF / 无用 / 防御性, and the one thing it groups by is `step.four` — "this hand left my side holding a four". From 0.4.7, when the signal was introduced, through every release up to and including 0.5.6 补增 §三 后续, **nothing ever assigned it**: the two reads inside that pass were the field's only mentions in the entire extension. `uselessFour` was therefore structurally 0 — not rarely 0, but 0 by construction — and the weight the table spends on it (0.05 in 0.4.7, 0.06 in the restored table) never paid a single point on any game ever recorded. The re-scoring behind the paragraph above counted it among the terms that "scored zero in every one of the 127 sides"; the reason was this, not rarity. No suite could see it, and that is the more useful half of the lesson: **every fixture in `verify-047` and `t-data047` stamped `four` by hand**, so both suites were green for eight releases against a flag production never set. A synthesised fixture cannot fail the way production does.

`scoreStep()` stamps it now, from the board AFTER the hand. That is the right home for three reasons: it is the one function BOTH analysis paths call — `analyzeStep` (逐步, which the live session and the replay both drive) and `analyzeGame` (全局) — and both hand it the position after the hand; the predicate is the shipped `scanThreats(board)[side].four`, a 5-cell window of four own stones and one empty one, i.e. "an empty point that completes five", which covers 冲四 and 活四 alike and is exactly §1.1's 「你走一个冲四，对手必须应」; and it is a per-hand verdict derived from board plus engine result, which is what everything else in that function already is. The test is `newly` formed, not merely `has`: a four that already stood BEFORE the hand — the opponent declined to block it, or a 双四 left one line standing — is not a four this hand made, and counting it would extend a run by a hand that only inherited one. `prevBoard` is optional, and a caller that supplies none (an old harness) degrades to the plain "has a four" test rather than throwing. All three step literals now declare `four: false`, so the field exists on every shape rather than on some, and `slimStep` persists it — drop it there and an archive still renders, while anything that re-derived the runs from it would read zero for every game.

Measured on the operator's own corpus: of **1084 analysed hands, 223 (20.6%) made a four** — fours are ordinary gomoku, which is the whole reason `FOUR_RUN_MIN` is 2 and a lone four scores nothing. Those 223 hands form **33 runs: 29 VCF, 3 防御性, and 1 无用**. Only **one of the 127 scored sides** changes at all, by **+2.70** points (average side 46.91 → 46.93). Two things follow, and both are worth keeping. First, the 29-to-1 split is the classifier working: the overwhelming majority of four-runs in real games are a winning line being converted, and the pass correctly refuses to punish them. Second, the restored 6% is a **rare, high-precision** term rather than a lever — on this corpus it still pays on one game in 65, so an operator should expect 无用冲四 to read 0 on nearly every archive and to mean something when it does not. 绝望手 and 回避 remain 100% zero on the same corpus; those are separate signals with their own thresholds, not part of this fix, and they are left as they are.
**The 留空 figure is the shipped table, and so is what an empty box uses (P1).** The panel's per-signal reference had been reading the learner's table, so on any profile where 重新学习 had run the number beside every box was that training run's — on the reporting operator's, a 0.5.5-era table whose six statistics were all 10.5% and whose behaviour signals were 3.4% / 16.6%. That is the old numbers, and it also meant an empty box did not select the shipped default at all: the detector kept scoring with the learned table. Two tables cannot both be the baseline, and the operator's hand-tuned one is the default now, so **the weights are `shipped ⊕ your overrides` and nothing else**. 重新学习 still trains everything else it did — the thresholds, the ramp anchors, the risk cuts and the feature library — and it still records a weight proposal, which the 学习 panel prints with a note saying it is recorded rather than applied; the risk cuts it searches are computed on the shipped table, because choosing a 70/40 line against a scoring function nothing runs would make the learned cuts wrong for every game.

## 0.5.5

0.5.5 rebuilds the single largest term of the score, and gives the overlay the button its neighbour never was.

**好点池 redefined (P0).** A 好点 used to be a move inside the engine’s Top3. It is now a move inside the Top5, plus Top6–8 but only on the steps where the engine was actually asked for them — that is, where `thinkMs > 6000`. Asking for a deeper list on the slow moves and a shallower one on the fast moves is not a reason to measure the whole game against a line that only exists on some of it. The criterion is no longer 「three good moves in a row」 but two figures combined: 占比 — how large a share of the player’s own analysed, non-opening, non-exempt moves were good — weighted 70%, and 连续度 — the longest run — 30%. A share below 55% scores nothing and 100% scores full marks; a run shorter than three carries no penalty, deliberately, since an occasional bad move says nothing and only a run is a signal; from three upward it accumulates on a 1.25 power curve that saturates at fifteen. Black and white are computed separately.

The 活三 pool does **not** move: it keeps its own independent `liveThreePool` and is never counted into 好点池, so nothing is scored twice. The weight goes from 0.03 to **0.18**, level with 唯一手, and it is paid for out of the rest of the table — `out` gives up 0.07, `sharp` 0.04, and the remaining terms come down slightly — which takes the table from the 1.28 it has carried since 0.4.8 and normalises it to **1.00**. That is the part worth recording: 0.4.8 and 0.5.2 each wrote this change and each declined to make it, because both treated the odd-one-out pools as a SURCHARGE laid on top of the original six. The invariant is the whole table now, and the whole table sums to one.

In 查看器 the 指标汇总 gains 好点占比 and 好点最长连击, the 贡献分解 has a 好点池 item, and 步骤明细 gains a 好点池 column that ticks the steps which qualified and prints how far the run has reached.

**Overlay (P1).** The button labelled 「导入回放」 has never imported anything — it re-runs a stepwise analysis over the current game, so it is now 「重新分析」, which is what it does. The import it was named for arrives for real: 「导入至回放」 files the current game into the replay archive **by force**, stepping over both count filters (the ordered floor and the unordered ceiling) and the AI-rate filter, after a single confirmation. It is also the one-click remedy behind every 「未存档」 notice: a game held back by the move floor, by the count filter, by the AI-rate filter, or a report that came back empty for both sides — all four now state their reason and offer a 强制保存 link that performs the same action. **The save-filter panel, made readable (P1).** 0.5.4 drew the two-segment slider with every element §1.5.1's sketch listed except the labels. ## 0.5.2

0.5.2 adds two detection signals that only mean anything inside a run, fixes the P0 that showed an imported archive as an empty board, and finishes the update path, the question list and the panel’s look.

**Two pools, and the runs that feed them.** Every streak signal before this release was per-hand: one good move and ten good moves in a row scored the same. Two of the new signals walk a pool instead. The 好点池 counts a hand as a good point when it is Top-3 or better, starts scoring at three in a row and ramps linearly to twelve (weight 0.03). The 活三 pool is a separate walk: when the opponent really holds an open three and the engine’s top two candidate points are within a 0.15 winrate gap of each other, the hand is a 活三 defence — Top1 extends the pool, Top2 neither scores nor resets it (an ordinary player picks Top2 anyway, so it is not evidence either way), anything outside Top3 resets it, and a good point that is *not* a 活三 defence is skipped, which is what keeps the two pools genuinely independent. It grows as `1.3^n` from the second hit (weight 0.03). Both are **surcharges**: the six base weights still sum to 1.00 and the pool terms ride outside them, so an old archive with no pool signal scores exactly what it scored before. Scaling the six down to make room would multiply every stored risk score and flip games sitting on the 70/40 cuts — the same instruction 0.4.8 §1.2 gave and the same reason it was declined then. The ordinary Top1 streak and cumulative-hit terms also move from linear to exponential (`1.3^(n-2)` / `1.15^(n-2)`), because that is what a run means: each further hit is worth more than the one before it.

**一键更新, 方案 B.** The update banner’s download line becomes a button. The service worker fetches the GitHub zip through `chrome.downloads.download`, then raises a `chrome.notifications` notification whose button opens `chrome://extensions` so the operator reloads by hand. It is not automatic because an extension cannot modify its own files on disk — a browser constraint, not an omission — so 方案 B hands the last step to the only party that can perform it. The notification names the downloaded file and deliberately not its folder: without the `downloads.open` permission the path can only be guessed, and any profile that moved its download directory would make the guess wrong. Both banners — the in-page panel and the viewer — are now `[一键更新] [查看详情] [暂不更新]` in that order, and both route through the worker rather than calling the download themselves, so one implementation raises one identical notification whichever surface started it.

## 0.5.1

0.5.1 turns the detection engine from one hard-coded build into a registry with a fallback chain, adds a KataGomo server as a second engine, and lets the operator upload a weight package of their own.

**An engine is no longer one hard-coded build.** The 0.5.0 spec described an engine with a single field — `kind: 'wasm'`, `protocol: 'gtp'`, `builds: ['engine/katagomo-*-simd128.js']` — and that combination cannot exist. "How an engine is hosted" and "what we say to it" are two questions, so `engines.js` keeps them as two orthogonal fields: `kind` is `wasm` (a JS+WASM bundle in this package, run by `worker.js`) or `http` (a server the operator points us at); `protocol` is `yxboard` (Rapfi's `YXBOARD … DONE` / `YXNBEST n`), `gtp` (Go Text Protocol plus the gomoku extensions `kata-set-rule` and `kata-set-board-size`) or `katago-json`. KataGomo is a C++/CUDA fork of KataGo (`hzyhhzy/KataGomo`) whose releases ship native Windows and Linux binaries and `.bin.gz` neural nets — there is no WASM target and no road to one, so those two build files cannot be written. The spec's own §2.1.1 fallback already said so ("若 KataGomo 无 WASM 构建 → 只能作为服务端引擎"); 0.5.1 follows it, and KataGomo is an HTTP engine. The `gtp` protocol stays implemented and stays covered (§5 of the new suite drives its transcript through a stub worker) — it is simply attached to no engine, because attaching a protocol to an engine that cannot run it is precisely the class of mistake this project has paid for three times.

**The wire format is KataGo's analysis JSON.** The request body is the one the KataGo analysis engine itself parses — `{id, moves: [['B','H8'], …], rules, komi, boardXSize, boardYSize, maxVisits|maxTime}` — and the response is read from `moveInfos[].move` (the native field) or `moveCoord` (what one popular REST wrapper calls it), accepting both. Colours travel paired with their coordinates rather than implied by index, because the native format allows `initialStones` and handicaps and "the colour of move i is i % 2" is a rule this codebase already has too many copies of. `winrate` and `scoreLead` are from the side to move in **both** engines (`reportAnalysisWinratesAs = SIDETOMOVE` on KataGo's side), so neither is flipped; a `1 - x` here would invert every verdict in the product. The millisecond budget becomes `maxTime` and the server decides, because it is the only party that knows its own machine — only the liveness probe asks for `maxVisits: 1`, since its question is "does this answer at all" and not "how strong is it". Request ids carry a monotonic sequence number: `Date.now()` alone collides for every request inside one millisecond, and a server that de-duplicates by id would answer the second position with the first one's verdict, silently. And the coordinate alphabets are not interchangeable — GTP skips `I`, so fifteen columns run A–P, while the share string is fifteen lower-case letters with no skip; using one for the other shifts every column past H by one, producing coordinates that are wrong rather than absent.

**The fallback chain deviates from the spec on purpose.** The spec's chain was `[id, 'katagomo', 'rapfi']`. Falling back from a local engine to a remote one is not a downgrade — it ships the operator's game to a server they did not select, over a network, possibly in another country. A recovery may cost more time (a weaker build, a shorter search); it may not cost more of the operator's data. So an HTTP engine enters a chain only when it *is* the chosen engine, and Rapfi answers if it fails.

**A custom detection model is a weight package.** MV3's `extension_pages` CSP allows no `script-src` but `'self'`, `'none'` and `'wasm-unsafe-eval'`, so a user-supplied `.js` has no legal import route — it currently runs only because Chromium checks a blob URL against its inner URL (crbug 40945262), which is a recorded defect rather than a road, and the day it is fixed the feature would go with it. What is uploaded instead is a Rapfi `.data` weight package: at most 100MB each and at most five of them, stored in this browser's IndexedDB under 白身's own database (`bai-shen-custom-engines`) and never uploaded anywhere. `custom-engine.js` is loaded only in extension pages, because a **content script's `indexedDB` is the HOST PAGE's**, so the in-page panel can only ever learn the list through a message. The engine-side hook is one line: `worker.js` already remapped every `rapfi*.data` request onto the one shipped package, so now that single request can answer with a blob URL instead — the `.js` and the `.wasm` still come from this package, which is what keeps a user-supplied model inside `script-src 'self'`, and redirecting `locateFile` wholesale would send the wasm fetch to the weight package too. Verification is one real search on the package, because the package's own format is opaque (an emscripten file table plus NNUE weights) and there is no cheaper honest test; a failure names its cause and the package is discarded.

**One setting, four read-points, one sentence.** The settings dropdown, the detection page's dropdown, the replay detail's dropdown and the in-page panel's 「模型」 menu all share `settings.engineId` and one option-set builder — `setTxt` writes `textContent`, so the dropdown's label now lives in its own `<span>` rather than wrapping the `<select>`, and every rebuild puts the stored id back, which is the same lesson 0.4.11 §一.3 learned on the theme dropdown. The settings status line and the report's 分析引擎 row both read `engineSummary()`, so a KataGomo run cannot be described as 「多线程 16 线程」 on one page and 「服务端 · …」 on the other. The fallback record lives **on the Engine instance** instead of in a module variable: a module variable and the engine it describes have different lifetimes, and as a module variable one failed custom-model verification — whose chain steps down to Rapfi — made every later analysis in that session report 「已回退」, even after the operator had fixed the model and a fresh engine had loaded cleanly. KataGomo's address is an **optional** host permission, granted by the operator at the moment they first use it.

## 0.5.0

0.5.0 fixes a false stop that ended the record of a perfectly live game, names the one rule that had been implicit since 0.4.8, extends the preset questions, and gives the extension its real name.

**A jump four was being read as half of a 四三杀.** `scanThreats()` answers "is there a four" with a 5-cell window holding four of one colour and one empty cell — a test that cannot tell `XXXX_` from `XX_XX` or `X_XXX`. `applyTerminalShape()` then combined that "four" with a per-side open-three flag and called the position terminal. For a solid four that is right: the defender has one answer, it is at the end of the line, and it does nothing about the three. For a jump four it is wrong in two independent ways — the only completing point sits INSIDE the four, so one stone can answer both threats, and that same point is where the defender's counter-four would land. Detection stopped, and the rest of the game was never recorded. The board's shape is now read the right way round: `fivePointsFor()` enumerates every point at which a side would make five, and `classifyFour()` turns that into `solidFour` (the completing point at an end of the line), `jumpFour` (inside it) or `doubleFour` (two or more completing points, which covers the open four). Only a solid or a double four counts as the four half of a 四三杀; a jump four plus an open three is recorded and detection continues, because a stopped record is a permanently wrong verdict while a continued one is merely a longer analysis. The hand carries `jumpFourFlag` into the archive and the viewer marks it 「跳四」 — outlined rather than filled, because every other badge is a verdict reached and this one is a verdict declined.

**And the unique-hand exemption is now a named rule.** 0.4.8 exempted a hand whose defence was forced from the unique-hand streak and from the aggregate, by reading `forcedDefense` directly in two filter clauses. The behaviour was already what the spec asks for, but "exempted" was a property of a filter and could not be pointed at. It is `isExemptUnique(s)` now, defined as `!!(s && s.forcedDefense)` and deliberately NOT consulting `forcedDefenseHow`: whether a defence was forced is a fact about the board, while `shape` and `engine` are merely the two ways of noticing it, and an exemption that depended on which one fired would exempt the same hand on one path and charge it on the other.

**Two messages joined the bank.** `q-ask-origin` asks 「where are you from?」 in English alone, deliberately: it exists to make the opponent reveal their own language, so sending it in a guessed one would destroy the evidence it collects. `q-announce` is the anti-cheat statement, in all eight of the bank's languages, so the operator can send it by hand in whichever one the opponent is reading. Both carry `weight: 0` — they inform, they do not score. That is a value `grade()` could not express: it read `question.weight ? … : 3`, so an explicit 0 was falsy and was silently promoted to a weight-3 question that moved the risk score, exactly what a statement must never do. The grade path now reads `weight != null` and returns before any of the reply-classification tails, so a zero-weight message is graded as sent and nothing else. `q-announce` also has two entry points, and the 0.4.4 automatic sender still pins its own wording to English; `chat.js` derives both from the one bank entry (`announceText('en')` / `announceText(lang)`) rather than keeping a second copy of the sentence, and `announceTexts()` lets the panel recognise the statement in any of the eight, so sending it by hand is not silently invisible to the announcement record. The picker greys it with 「本局已经发过声明」 once it has gone out.

**The extension is 白身 / Baishen.** The name is not a description and not an acronym; it is the shade of the stones on the board — and, in this tool's own vocabulary, the one that is hardest to see. Chinese interfaces read 白身; every other interface reads Baishen（白身）, because a transliteration the operator can search for is worth more than a glyph they cannot type. It reaches the manifest (name and the 132-character description), the overlay header, the viewer's `<title>` and `<h1>`, the copy-output prefix in all thirteen locales, and the tutorial's first line.

**And the runtime dictionary is finally checked against the baseline table.** Keys that are built at runtime — `TO('verdict', code)`, `T('learn.weight.' + k)` — are registered in two places: `_tools/i18n-extra.js`, which the generator reads to emit the twelve translated tables, and `locale/zh-CN.js`, which is the baseline `t()` resolves against. Nothing verified that the two lists agreed, and they had drifted: `learn.weight.evasion` and `learn.weight.winBlunder` were in neither translated table's source of truth nor the baseline, so the contribution breakdown rendered the raw slug `learn.weight.evasion` in Chinese, and the eleven threshold rows added alongside them were latent in the same way. Worse, `learn.weight.sharpStreak` and `learn.weight.sharpTotal` were in no dictionary at all — `paramLabel()` falls back to the canonical Chinese label, so the learner's weight table read 「唯一手连续」 in every language including English. 0.5.0's own `verdict.none` would have shown the operator the word `none`. The missing rows are filled in, the two labels have real translations, and the newest suite now walks the three sets (runtime dictionary → baseline → generated tables, plus every `WEIGHT_LABEL` / `THRESHOLD_LABEL` entry in `learn.js`) so the next omission fails a test instead of shipping.

## 0.4.12

0.4.12 fixes one border-state defect, found in a real game: the border is a second, glanceable readout of the numbers on the panel, and at the end of a game it was contradicting them.

**A finished game cancelled its own verdict.** The two cards read 「黑方 73.5 · 高风险 / 白方 72.8 · 高风险」 and the border breathed blue — i.e. 待机. §2.2 states the priority explicitly: 黑名单提醒 > **检测结果** > 检测启动 > 就绪 > **待机**. §2.1's table defines 待机 as 「未加入对局 或 对局已结束」, and the first implementation of `borderStateFromPanel()` tested `ended` up front — so the last entry of that table outranked the verdict it was written to sit beneath. The moment a game ended, the border dropped whatever colour it was showing and went back to breathing.

That is the exact failure `paintBorderState()`'s own comment forbids — the border is not an independent indicator, it is the same facts the status line spells out, read at a glance — and the end of a game is the worst possible moment to lose it, because that is precisely when the verdict becomes FINAL. The operator's answer to "was that a cheater?" arrives at the whistle, not at move 30.

检测结果 is tested first now: if a report is on screen (the numbers on the cards), its colour wins; with no report, 「对局已结束」 is still 待机. The two branches are one line apart and both halves are asserted. `inGame || ended` keeps the rest of 待机 intact, so a report that is not about the board in front of you — 导入回放 on an empty board — still reads as 待机.

The regression test is behavioural rather than textual. `behave-049-border.cjs` §6b boots the real `content.js`, hands the stubbed engine a 高风险 report, and drives the real 「对局结束 → 收尾分析」 path. It asserts the border is red and STEADY, that the cards say 73.5 / 72.8 in the same paint, and that lowering the risk to 可疑 and then to 低 switches directly with no flash — §2.1's 「风险降级时…直接切换」, after the game as well as during it. The twenty-move fixture is deliberate and the reason is recorded in the file: a game shorter than 最小存档 (14) is refused by `finalizeGame()` before it ever creates the 收尾分析 job, so a shorter fixture would have re-proved the no-report case (§5) instead of the one that was reported.

## 0.4.11

0.4.11 fixes nine defects that were all silent — none of them throws, none of them is visible as an error, and each one produces a WRONG verdict under a specific condition, which is the one failure mode an anti-cheat tool cannot afford. It also annotates each preset question with its wording in the interface language.

**The live stepwise analysis has been colouring the board by guesswork.** `content.js` sent the colours of the PREFIX (length = moves − 1) and `offscreen.js` compared that against the length of the whole move list. The two numbers differed by one for ever, so the board was always null and every later colour fell back to index parity. On a clean record parity is exactly right — right up until a move is dropped as a repeated coordinate, or marked as reconstructed after a mid-game join, or an AI reference stone sits in the middle. From that move on every colour shifts by one, the engine reads a four that is not on the board, `uniqueBlocksForFour()` counts two defences instead of one, and the hand that should have been exempted is not. 0.4.8's shape-first forced defence had therefore never once fired on the live path. The whole board's colours now travel, and the colour of the move being scored is read from `record.stones[pos]` — the stone that survived de-duplication, not the raw entry.

**The viewer was building a second engine.** It loads `app.js`, so its own `getEngine()` called `new Worker('worker.js')` inside the extension page: a second Rapfi, a second 40 MB data package, a second pthread pool, and a second analysis queue that `content.js` could not see. Both sides then resolved `settings.threadNum` independently and could oversubscribe the machine. The viewer now holds no engine at all — 全局分析, the sample editor's AI 分析, AI 思考 and pause/resume all arrive at the offscreen document, where the one engine and the one FIFO queue live. Pausing a one-shot job needs `gm-pause`/`gm-resume` because its `pauseCtrl` holds `_resume`, a function no message can carry: the object stays in the offscreen document and is looked up by job id.

**The theme dropdown was frozen in Chinese.** `var THEME_LABEL = { light: T('viewer|浅色'), … }` resolved its three `T()` calls while the module was being evaluated — before `boot()`'s `applyLang()`. On an English interface the 主题 select read 「浅色 / 深色 / 跟随系统」 for the life of the page. It is a function now, rebuilt whenever the language changes. This is the rule `i18n.js` keeps repeating: **any `T()` evaluated before `applyLang()` freezes on the default language.** Making the select rebuild exposed the other half of the same defect, and the behavioural harness found it rather than the spec: assigning `innerHTML` to a `<select>` drops it back to its FIRST option, so an operator on 深色 who switched the interface language watched the 主题 dropdown snap to 浅色 while `<html data-theme>` stayed dark — the control stating a value other than the one in force. `fillSettingsForm()` restores the selection.

**An archive's name stopped looking like a default the moment you switched language.** "Is this name still the generated one?" was a string comparison against a freshly generated name, and the generated name embeds `T('archive|黑')`, `T('archive|手')` and `T('archive|和棋')`. A name written in one language never equals one written in another, so every old archive grew an 「原命名」 line and its title turned from 「A VS B」 into the whole 「A VS B 黑72/白85 全局 42手 …」 string. The fact is recorded at generation time now (`nameIsDefault`), a rename clears it, and archives written before 0.4.11 still fall back to the string comparison.

**The detection page's metric table was two generations behind.** It carried its own hand-written eight rows while the replay detail rendered the shared builder — so 0.4.7's 冲四序列 / VCF / 防御性冲四 / 无用冲四 and 0.4.8's 唯一手最长连续命中 / 唯一手累计命中 existed in only one of the two. The same game showed two different sets of numbers depending on which pane you opened, which is the entire reason the shared builder exists. The detection page calls it now.

**The question picker offered languages the bank cannot speak.** It listed all thirteen interface languages while the questions exist in eight. Choosing Vietnamese or Arabic sent the question in English in silence, and the footer apologised afterwards — after the question had already gone out in a language the operator had not chosen, which is exactly what 0.4.10 §2.3 promised would never happen. The list is computed from the bank's own data now, so the path is gone rather than merely reported.

**A blacklist entry added by hand was filed as coming from the overlay.** `source: 'overlay'` was hard-coded, and the viewer's 黑名单 page — where there is no overlay and no game in progress — goes through the same function. `source` is a parameter now, defaulting to `manual`, with the overlay saying so explicitly and the importer marking what it brings in. The column had always been stored and never rendered, which is precisely why nothing noticed.

**The MAIN-world event channel had no shape check.** The listener verified only that the payload parsed as JSON and claimed `source: 'socket'` — it did not constrain the event kind, did not check that `moves` was an array, did not check that `count` agreed with its length, and did not check the snapshot's clock against the local one. This is not a security boundary (a MAIN-world script can read and write anything on the page), but it is engineering hygiene: any statistics script, ad frame or CDN shim on the page that happens to dispatch a same-named event would have its payload merged into the captured record. There is a whitelist of kinds plus the length and clock checks now, and a rejected frame leaves one `console.warn` — visible to a developer, invisible to the operator. The count check has one deliberate softening: `hook.js` prunes recorded stones the board no longer shows and counts them in `dropped`, so a lower count is accepted exactly when that witness has grown. A bare "count must not decrease" would drop a genuine resync frame, and a dropped frame is a quietly wrong record — worse than the collision the check exists for.

**And `minimum_chrome_version` is declared.** The code uses `storage.session.setAccessLevel()` (Chrome 102+), `chrome.offscreen` (109+) and `runtime.getContexts()` (116+, with a fallback). Without the declaration an old browser does not refuse to load the extension — it just fails to create the offscreen document, over and over, with an English `lastError` as the only clue. The floor is 109: `offscreen` and `storage.session` are both there, and `getContexts()` takes its documented fallback (the create-and-swallow path in `background.js`).

§二 is small by comparison and exists for one reason: a question is shown in the language you chose to ASK in, and nothing stopped you from choosing one you cannot read. Each row now carries, in brackets underneath, what the question says in the interface language you are reading — omitted when the two are the same, and replaced by 「（无 X 翻译）」 when that language has no wording for it.

Two of the nine are the same mistake 0.4.10 §一.1 made, in two more places: a value resolved before the language was known (the theme labels), and a comparison made across two languages (the archive name). Both are the shape a silent defect takes here — no exception, no log, just a wrong answer under a condition nobody tested. The theme dropdown losing its selection when the label was rebuilt is a third instance of that shape, one step removed: a control that shows a value the program is not using.

## 0.4.10

## 0.4.9

0.4.9 adds a local blacklist of registered players, and gives the panel's border a state.

**The blacklist is keyed on the username, not the display name.** A player on gomoku.com has two identities and they are not interchangeable: a `playerId` (`pneumonoul`), which is unique, uneditable and stable, and a `displayName` (`宇髓天元突破`), which is editable and repeatable. Only the former can recognise the same person on a later day, so the id is the key; the display name is stored beside it as a label, refreshed on every meeting and never matched on.

Three routes supply the id, tried in the order the spec names and each one defensively, because only one of them could be confirmed against the live DOM. The page's `<meta name="playerId">` comes first — but a meta pair on a *game* page is rendered per session, so it far more plausibly describes the logged-in user, i.e. us; it is therefore honoured only when its display name actually matches the opponent's and its id is not the operator's own seat. The socket is next, and it is the route that was always going to be right: `game-start` ships `players[{ id, name, color }]` and the id has been forwarded since 0.4.4 — this is the first release that reads it. The profile URL (`/xx/profile/<username>`) is the last resort, useful when the operator has the opponent's profile open. Whichever route answered is named in the panel on the player line, because a wrong id is only fixable if the route that produced it is on the record.

In the panel, a 🚫 button joins 查看器 and 📋 in the header. Grey means "not blocked" and red means "blocked" — red because that is this project's data ink for "this is the bad one" — and both states confirm before writing. It is greyed and inert in the three situations where the feature genuinely cannot work (spectating, a guest seat, or a game where no route resolved a username), rather than offering a click that would silently do nothing. When a game starts against someone on the list, the border flashes red three times and a red line names both the display name and the username. The list itself lives in a new 黑名单 tab of the viewer: seven columns, add-by-hand with an optional note, edit the note, remove, and import/export on the same JSON envelope the archive and sample libraries use. Everything stays in `chrome.storage.local`; there is no endpoint, no telemetry and no share path anywhere in the extension.

**The border is the other half: a state indicator.** Six states, driven from the same paint that draws the status line, so the border and the numbers cannot disagree. 待机 breathes blue while nothing is being watched (before a game, and after one ends); 就绪 is solid blue once a game exists but nothing has been analysed; the first detection of a game flashes green three times and then settles green; a finished analysis is green below 40, orange from 40 and red from 70 — and entering the red flashes twice first, while leaving it cuts straight across, because a downgrade is not news. When two players are analysed at once the border shows the higher risk, since it is the panel's alarm rather than a per-side verdict (the cards carry those). The blacklist alert outranks all of it and hands the border back to whatever it should have been showing when it finishes. The flash is also backed by a timer, because `animationend` never fires on a hidden element and a border stuck on a flash class would stop indicating in silence. The colours are literal and deliberately not themed: the colour *is* the meaning, the same reason the risk numbers and the semantic badges are exempt.

**The state belongs to the host, not to the panel body.** It is one `data-bs` attribute on the shadow host, and the CSS reaches `.gm`, the 缩略 body (`.gmcp`) and the 48px 图标 face (`.mface`) from it. Both halves of that matter, and the first release of 0.4.9 got both wrong. A class on `.gm` dies with the node, and `.gm` is replaced wholesale by a shell rebuild — which is what a language change does — so the border silently went blank and stayed blank, because the state was remembered in a variable that still said "nothing changed" about a node that no longer existed; the same variable guard also swallowed the very first paint, since it started out already saying 待机, which meant the resting panel — the state an operator is in most of the time — showed no state at all and looked exactly like the previous release. And `.gm` is `display:none` in 缩略 and 图标 mode, so an indicator drawn only there disappears in the two modes an operator shrinks the panel into precisely in order to watch it. The 待机 breathe also pulses the line's own colour rather than two alphas of one colour: varying only the alpha leaves the RGB identical at every frame, so the 2px line reads as a static blue frame while a halo moves behind it — 「蓝色呼吸灯」 that does not visibly breathe.

## 0.4.2

*(Written for the changelog, like 0.4.1 — the entries above are the verbatim manifest history. The same text is shipped to installed copies through `version.json`'s `releaseNotes`.)*

0.4.2 identifies the opening of a game the detector joined late, and adds a third kind of suspicious hand. Identification used to require three stones in order; it now falls back on position, because black 1 is pinned to tengen by the definition of an opening — so with two stones on the board (black tengen plus one adjacent white) the family is all that can be known and all that is claimed (直止 / 斜止), and with three stones whose order was never captured each stone's role is recovered from where it stands (one black on tengen, one adjacent white, one black inside the central 5×5) and the exact opening is named; an unordered board of four or more still refuses, because a later black stone sits in the same central square and "black 3" stops being identifiable inside the set. `detectOpening` now reports a `stage` of `opening` or `family`, a family capture is shown as 直止（大类，具体开局待定）, and it deliberately writes no opening name into the archive — but the archive does carry a derived opening family, so the 大类 filter still finds such a game instead of filing it under 未识别, which is what the one-shape-one-answer rule at the list card requires.

The new detection technique is the evasion move: one deliberately bad hand — a loss of at least 0.20 win rate, and not the top pick — planted between two good ones (both Top-1, both under 0.05). That hand is then *excluded* from the main statistics, because a deliberate blunder would otherwise dilute the very Top-1 agreement, ACPL and outside-Top5 rate that it is evidence about; the operator would be shown a human-looking ACPL produced by the smoke screen rather than by the play. Two further signals carry the evidence instead, and both are scored: a regular rhythm of evasions (three or more, with the coefficient of variation of the gaps between them — evenly spaced scores high, noisy blunders score zero) and 将胜乱下, a hand that gives up 0.20 of win rate while the side was already winning (best move win rate ≥ 0.85), which is counted whether or not the hand qualifies as an evasion — throwing away a won position is reported on its own. The step table gains a sixteenth column with its own teal badge, the metric summary gains 回避手 N 次（规律性 X）and 将胜乱下 N 次, and the contribution breakdown gains the two new terms. Their weighting is deliberately a surcharge and not a re-split of the same 1.0: the six 0.3.1 terms keep their own sum of 1.00 and the two new ones carry 0.06 and 0.04 on top of it, so a game with no evasion scores bit-identically to 0.4.1 (verified to 1e-12), and the learner normalises the two groups separately so neither can quietly eat the other's budget. All five thresholds are configurable and learnable. Switching language also repaints the archive and sample detail panes now, which are built in JavaScript and used to stay in the load-time language while the column menu beside them switched.

## 0.4.3

*(Written for the changelog, like 0.4.1 and 0.4.2 — the entries above the 0.4.1 heading are the verbatim manifest history. The same text is shipped to installed copies through `version.json`'s `releaseNotes`.)*

0.4.3 fixes a blind spot on the only-move scale and builds two features on top of the fix. The blind spot was that "playing like the engine" was measured exclusively as Top-1 agreement: a hand ramped from 0 below 72% Top-1, and the only-move term counted a sharp hand only when the played move *was* the single best one. But an opponent who consistently lands on the second through fifth best move is not playing like a human either — a strong engine still finds most of those hands within its top five — and a game of such hands scored in the fifties where it should have scored in the eighties. A near-miss is now graded rather than ignored: a new proximity step gives the Top-1 pick 1.0, the Top-2/3 picks 0.75 and the Top-4/5 picks 0.55 (anything worse, 0), the Top-1 ramp reads the average of that step across the side's hands instead of the Top-1 hit rate itself, and the only-move term averages the same step across the sharp hands instead of counting hits — so a sharp hand that takes the second-best move now counts, at 0.75. The two old Top-1 cut lines stay in storage and in the learner, but the detector only reads them when the caller explicitly asks for the legacy behaviour, which is what makes the before/after comparison testable; the new cuts ship at 0.50/0.90 and are themselves configurable and learnable, re-anchored on the quantity the ramp actually reads rather than on the hit rate it no longer uses. Nothing about the weight structure changed: this is a new set of thresholds, not a re-split, so the six terms still sum to 1.00 with the two 0.4.2 surcharges on top and a game with no evasion is untouched.

The first feature is segmentation. Every one of a side's own hands is classed as inside or outside the top five, that binary sequence is run-length encoded over the side's own move order (the opponent's hands are not part of the run — 段 counts *my* hands), runs shorter than three hands are merged into the neighbouring run so a single lucky excursion does not carve the game into noise, and the result is mapped back onto global move numbers and stored as `report.segments`. All four step tables draw it as a 4px left rail on the row's own move number — green for a run that stayed inside the top five, orange for one that left it — a heavier rule at each boundary, and a one-line legend under the header. The segments are editable: an operator can drag either edge of a run with a live preview (each side keeps at least one hand, so a drag clamps rather than empties a segment), or right-click a hand to create a segment of one move, to the end of the current run, or over a hand-picked range, and right-click inside a manual segment to discard the overrides and go back to the automatic rail. A hand-picked range is re-coloured from the hands it actually contains rather than inheriting both ends, so a range spanning both classes splits into two correctly coloured pieces. The manual list is per side and per game, persisted through the same serial write chain as everything else, and additive: a pre-0.4.3 archive simply has no manual list and renders the automatic rail.

The second feature is a classification on top of the score. The five bands of the risk number now have names, and inside the AI band the class depends on segmentation: a side whose hands stayed in the top five throughout is a low-level AI, one with a few hands outside is an evasive AI, and one with four or more is a strongly evasive AI — while the four bands below are 疑似AI, 职业选手, 高手玩家 and 普通玩家. The class is shown as a badge on the archive and sample list cards and in both detail panes, and can be overridden by hand from a dropdown, which marks the badge and updates the list; the override is stored beside the automatic answer rather than replacing it, so clearing it restores the automatic one. As with the risk levels, the class is persisted as a stable code (it is computed in the offscreen document, where no UI dictionary exists) and only its display is translated — the seven codes were added to the semantic core and to the runtime-key map so all eight tables carry them.

Finally, the sample editor showed per-step verdicts after an analysis but never the number they add up to. It now carries an 评估结果 panel with the same two risk cards and the same metric table as the detect pane and the replay detail — one renderer, so the three panes cannot print different readings of the same game — filled immediately when an already-analysed sample is opened, refreshed when a run finishes, and cleared back to 分析后显示 the moment an edit invalidates the board it described.

## 0.4.4

*(Written for the changelog. The same text is shipped to installed copies through `version.json`'s `releaseNotes`.)*

0.4.4 gives the detector a voice, and makes it ask. When a game starts it sends one fixed anti-cheat statement into the game chat — English, once per game, within the first thirty seconds, and only after the operator has confirmed it the first time, because talking to a stranger on someone's behalf is not something an extension should start doing on its own. From then on it answers in the language the opponent actually wrote in: the reply language is chosen from the message itself (CJK ratio, kana, hangul, Cyrillic, Latin stopwords, with full-width ？ and half-width ? told apart) and is deliberately independent of the interface language, so a Chinese UI can still answer a Russian opponent in Russian; eight languages of greeting/thanks/where-from templates rotate at random with a ten-second floor and no immediate repeat, and a message that carries no recognisable language at all gets one line — "where are you from?". Whoever sent a message is identified in three falling-back levels — the socket's own player list, then the page's DOM, then the announcement anchor — and the answer is allowed to be *unknown*: when the sender cannot be placed, nobody's risk number is touched. The one automatic exception is the opening question, which is only asked of a side already above 65%.

The second half is the F&Q: a bank of questions, transcribed from the operator's own file as a dialogue tree rather than a flat list, asked by hand from a button in the panel or automatically past the 65% line, with a sixty-second window for the answer. The first question asks whether the opponent has studied gomoku — a plain yes lowers the AI rate, a no raises it — and the second only exists once the rate is past 55%: it asks whether the opponent can name this game's opening, and if they say they are a beginner it follows up by asking them to name it for you, grading the answer against all 278 opening names across the eight languages (not just the current one) and closing with a thank-you. Grading maps to a verdict — correct, wrong, an explicit refusal, an off-topic answer, or no answer at all — and only the last two are free: correct costs −10, wrong adds +8, and the whole channel is capped at three adjustments per game and a cumulative swing of ±20, always applied to the opponent and never to the player. Finally, an optional LLM endpoint (default off, key stored locally and nowhere else, request routed through the service worker so the page's origin cannot bind it) can be used for the questions the bank cannot cover; it falls back to keyword matching on failure, and disables itself for a day after three failures in a row.

## 0.4.7

0.4.7 adds a detection signal, tightens an existing one, and gives the UI a theme.

The new signal is a run of fours. A single four is ordinary gomoku — you play a four, the opponent must answer it, the game moves on. What is not ordinary is a side that keeps making fours that have no point: they force a reply, gain nothing, and are made again. `markFourRuns()` walks each side's own sequence, groups consecutive fours into runs of two or more, and labels each run by the win rate the side had BEFORE the run started — copied onto every step as `prevBestWR`, because the rate at the moment of the four is the rate after it already worked. A run that started from a winning position (≥ 0.90) is a VCF and is not scored at all: that is a winning line being executed, not a symptom. A run that started from a lost position (≤ 0.10) is 无用冲四 and is the one that scores. Everything between is reported as 防御性冲四 and contributes nothing, because "the opponent was threatening and this was the only reply" is a legitimate reason to make a four and the run is the defence, not the offence.

The surcharge `aUselessFour` joins `evasion` and `winBlunder` OUTSIDE the six base weights, which still sum to 1.00 — the same arrangement 0.4.2 established, and for the same reason: the six terms describe how the moves look, and these three describe a pattern across moves. Weight is 0.05 (the spec named it twice at that value; the sentence comparing it to 将败冲四 would have put it at 0.08, and for a brand-new signal the lower number is the safer one to be wrong at).

Top2-5 proximity is raised again: 1.0 / 0.80 / 0.50 for Top1 / Top5 / Top8, and the `topProxLo` ramp now starts at 0.45 instead of 0.50. The three tiers replace the old two, so a Top3 hand no longer scores identically to a Top1 one — 0.4.3 §1.1 had already made this point and this is the next step along it.

阶段性臭棋 is now a property of the SEGMENTATION, not of the classifier. The merge pass that used to fold a short `low` run into its neighbours now skips `low` runs entirely, so a burst of bad hands inside an otherwise strong game survives as a run instead of being smoothed away — and that run is exactly what the classifier reads. Classification counts them: no low runs is 低级AI, one run of two or fewer hands is 规避型AI, and two or more runs OR any single run of three or more hands is 强规避AI. The "or" matters: one long collapse and two short ones are different stories but the same verdict, and a classifier keyed on the count alone would call the second one a weaker player than the first.

The engine is asked for Top8 instead of Top5 when the recorded thinking time exceeds 6 seconds. A hand that took that long is a hand the player was computing on, and the extra candidates are the evidence of what they were choosing between. It is per-step, not per-game, and the column is now 「候选（前5/8）」 so the header does not claim a width the data may not have. The step-table legend repeats the rule inline («TOP8 扩展（思考 > 6s）»), because a reader who does not know about the 6-second cut reads four empty candidate cells as "the engine found nothing there" rather than "this run did not ask".

All three four-run classes are reported, in two places. The 指标汇总 table gains a 冲四序列 total plus one row per class, and the detail pane's fact list carries the same three numbers on one line — VCF and 防御性 are shown even though only 无用 moves a score, because a column of zeros under two labels is the clearest possible statement that those two are not being punished. The 贡献分解 panel used to print its components as their raw identifiers, so the new term read `uselessFour 2.5`; it now resolves them through the same `learn.weight.<key>` runtime key the learner's own weight table uses, which is also what keeps the panel and that table from ever wording one component two different ways.

Two panel fixes. The compact (缩略) face was sticking at 99%: its finished-check ran AFTER the running-check, so a job whose progress had reached 99 while still marked 分析中 kept drawing the progress bar even after it finished — and the one number that would have ended the loop was the one the check never reached. `liveFinish()` now sets the progress to 100 unconditionally, and a failing job is floored at 99 rather than left at whatever it had reached. Both are the same bug from opposite ends: a progress that never arrives at its terminal value.

And the theme. `settings.theme` is `dark` / `light` / `auto`, defaulting to `auto`, with `auto` resolved by a CSS `prefers-color-scheme` media query rather than in JavaScript. That is deliberate: the attribute is the only thing JS writes, so there is no flash of the wrong palette on load and no listener to keep correct — an OS theme flip repaints because the stylesheet says so. The panel gets it on the Shadow Host (`data-theme`), the viewer on `<html>`; both are the root of their own document, which is why they are not the same line of code. In the light palette the step tables' black and white rows swap their wash values (`#1a1a1a` / `#e8e8e8`), because a `#DCDCDC` row on a white panel is nearly invisible and a `#111` row would be the only dark object on the page.

Transparency mode is a window-level effect only, and the settings page says so. A `chrome-extension://` window is composited by the browser with no per-window alpha, so "transparent" means transparent against the browser's backdrop and cannot show the desktop — promising otherwise would have been the kind of claim that reads fine in a changelog and is obviously false the moment it is used. Within that, the two alphas are deliberately separate: the background surfaces fall from 1.00 to 0.00 with the slider, and the functional widgets stop at 0.80. A window whose buttons are as invisible as its background is not a feature, and the floor is what keeps the close button on screen at level 0.

### §1.1 冲四豁免改为形状优先

The forced-defence exemption under-reported in the live stepwise detector: a hand that was the only answer to the opponent's four still counted in the main statistics. The criterion was the engine's own numbers — `bestWR != null && gap >= 0.15 && top1` — and in the live path that is unreliable four ways: at the 2000 ms budget the candidate list is short enough that the top-two win rate (and therefore `gap`) is understated across the board; 0.4.7's TOP8 extension can push a low-scoring candidate into second place and *shrink* `gap`; the engine's own score jitters across two runs of the same position; and, the main cause, a four's blocking points are frequently symmetric, so the engine returns one of them, the operator plays the other, and `top1` — which is `eqCoord(actual, best)` — reads false on a hand that had no alternative at all.

None of that has anything to do with what the board allows, so the uniqueness is now decided from the board. `uniqueBlocksForFour(board, side)` enumerates every empty point that, once `side` plays there, removes the opponent's four — that set *is* the side's legal defences — reusing `scanThreats` (never the engine); `forcedDefenseByShape()` runs it on the position *before* the hand being judged and returns forced exactly when the set holds one point and that point is the move actually played. The engine verdict is kept and OR-ed in, so a hand the engine already recognised is unaffected, and `step.forcedDefenseHow` records which of the two fired (`shape` / `engine`). The `gap` cut moves with the budget — 0.12 at 2000 ms or less, 0.15 otherwise — which is the spec's second change. A live four (`_XXXX_`) deliberately does *not* qualify: no single point removes it, the set is empty, and the shape pass declines rather than inventing a forced block — that position belongs to §1.3's live-four path.

### §1.2 唯一手连续命中

A single sharp hand — the engine's only good move — is ordinary; a *run* of them, each played as the engine's own first choice, is a different claim about the player, and it is the point at which "good at gomoku" stops explaining the sequence. `sharpStreakStats(steps, side)` walks the side's own move order (the opponent's intervening hands are not part of the run; opening hands, un-analysed hands and the §1.1 forced-defence hands are skipped, so the two features never count the same hand twice) and returns the longest run of top-1 sharp hands and the total number of such hits. A sharp hand that *missed* the top move breaks the chain; a hand that is not sharp at all leaves it standing, because it is neither a hit nor a failure to hit. The running position inside its run is stamped on each step as `sharpStreak`, so the step table can draw 「唯一手（连续 K）」 without re-walking the sequence — a second copy of that walk in the viewer is exactly the kind of duplicated answer this project has shipped wrong three times.

Two terms are built on it: `aSharpStreak` ramps from three consecutive hands (`clamp((max − 2) / 7)`), `aSharpTotal` from three cumulative hits (`clamp((hits − 2) / 18)`). §1.2's weight table wrote all eleven weights as one set summing to 1.00 — which would have dragged the six down to 0.81 and moved every archived score — and its own acceptance criterion #5 says the risk score must be unchanged when no sharp hand is hit. The operator chose the criterion, so the six keep their sum of 1.00 and the two new terms (0.04 / 0.03) join `evasion`, `winBlunder` and `uselessFour` as surcharges *on top*, clamped at 100; a game with no sharp streak scores exactly what it scored before. The metric summary gains 唯一手最长连续命中 and 唯一手累计命中, and `learn.js` mirrors the walk with its own pure `sharpStreakFigures()` so the learner reads the same number the detector did.

### §1.3 终止机制完善（反四检查）

`applyTerminal` is split in two. The synchronous `applyTerminalShape()` keeps the 0.3.7 priority list unchanged — a four-three is a kill before a live four is — but the four-three half now runs a counter check before it stops. `checkFourThreeCounter()` enumerates the points that answer the attacker's four (the same `uniqueBlocksForFour` set) and asks whether any of them also forms a four *for the defender*. If one does, that is a 反四: the attacker must answer it, the open three never becomes a live four, the game continues, and stopping there threw away the rest of the record. Only then does the old stop apply. A live four still takes the fast path with no counter check, and a check that cannot be run (a missing engine, an unknown side) degrades to a conservative **non-stop** with `step.stopCheckFailed` set rather than inventing a result. The viewer shows the exception as 「四三被反四（第 N 手）」 so an operator can see why the analysis did not end.

### §2 MV3 对齐

`manifest.json` was already `manifest_version: 3` and already using `chrome.offscreen`, `world: "MAIN"` and `optional_host_permissions`; the alignment work is therefore the transient state. The run's `archivedEpoch` / `liveStopped` / `gameEpoch` and the chat language now live in `chrome.storage.session` instead of `chrome.storage.local` — that area is memory-only and cleared when the browser closes, which is what "transient" means, and it stops writing a per-game scratch value to disk. Because `chrome.storage.session` defaults to trusted contexts only, `background.js` raises it with `setAccessLevel({ accessLevel: 'TRUSTED_AND_UNTRUSTED_CONTEXTS' })` at start-up, or the content script could not read it; on a Chrome without that API the code falls back to `local` and everything still works. The module variables stay as the synchronous working mirror and `hydrateSession()` refills them on boot.

### §3 LLM 模型选择器

The Model field in the LLM panel was a bare text input. It is now a `.model-picker` drawer over the same input: a preset list of 21 mainstream models across OpenAI / Anthropic / DeepSeek / 智谱 / 阿里 / Google / Moonshot / 字节 / 本地, a search filter that works in Chinese as well as English (Chinese goes through a `MODEL_ZH_ALIAS` table, so 「智谱」「深度求索」「通义千问」「豆包」 all reach the right entries — matching only the English id would have filtered those to nothing and the drawer would have looked broken exactly when it was being used), click-to-select which writes the id back into the field, and a free-text path kept intact, because an allow-list would be wrong the day a vendor ships a new name. Clicking outside or pressing Escape closes it, and a query nothing matches says so and points at the field rather than showing an empty drawer.
